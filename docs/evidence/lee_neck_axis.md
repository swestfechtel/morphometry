# Lee's proximal neck axis: the index-frame invariance work

How `contour_femoral_neck` came to depend on the array bounds, what the replacement does, and how
the three crop residuals were closed one at a time. Moved verbatim out of `CLAUDE.md`, which keeps
the replacement construction, the quirks that were deliberately preserved, the `_NECK_ENDPOINT_ROUNDED`
lever, the residual grid-phase sensitivity and the do-not-pool burden.

The closing result: 5 of 100 halves reproduced their own landmark under a pad before, 100 of 100
after, and with the last residual fixed the Lee neck centre follows a margin-0 femur-bbox crop on
100 of 100. The package now contains no image-rotating landmark transport at all.

**A note on cross-references.** These paragraphs were written inside `CLAUDE.md`, so an
"above", "below" or "recorded here" may point at a bullet that stayed there rather than at
something on this page. Nothing was reworded, which is the point; the file it came from is
`CLAUDE.md` and the two are meant to be read together.

## What the old two-rotation notch search did, and which half leaked

**Lee's proximal axis is index-frame invariant, and that closes the task #9 family (2026-11-05).** `femur.py::contour_femoral_neck` located the intercondylar notch by **rotating the selected 2-D layer twice** (`utils.rotate_mask_dorsal_points`, i.e. `skimage.transform.rotate(mask, -angle, resize=True, preserve_range=True) > 0`), searching the **resampled** raster, and mapping the result back through shape-derived offsets (`rot_offset`, `rot_center`, both `int()`-truncated). All of that served one scalar: `a = |notch − head_centre| / r`, which sets the two radii `r_1 = (a − 0.1)·r`, `r_2 = (a + 0.1)·r` that crop the neck contour — the mapped-back notch's **direction is discarded**, which is what licensed removing the map-back entirely.

**Both halves of the mechanism leaked**, measured over the 100 Augsburg reader-study halves: the *first* rotation angle was already **exactly invariant (100/100)**, but the second — computed on the already-resampled raster — was exact on only **9/100** (median 1.40°, max **21.19°**), the mapped-back notch on **0/100** (median 1.11, max 9.77 voxels), and `a` on **0/100** (median 0.046, max 0.527). So correcting only the map-back would not have worked. Three of those four figures were reproduced to the digit by two independently written probes.

## Exposure on the production path

**Exposure, on the production path.** Worst over four pads at each end, 100 halves: the Lee neck centre was reproduced on **5 of 100** (median 2.5, p90 7.1, **max 30 voxels**) and the proximal axis bearing on 5 of 100 (median 1.56°, p90 4.70°, **max 20.27°**); 66 of 100 moved by more than 1° and 10 by more than 5°. A **high-end** pad — which changes no anatomy index at all, so a correct landmark must be *bit-identical* rather than merely shifted — is the sharper and strictly worse probe (max 30 voxels / 20.27° against the low-end pad's 21 / 14.93), the same probe task #5 quotes for the condylar line. For scale the Lee torsion's cohort SD is 14.58°, so the worst case is comparable to the measurement's entire spread. The head centre contributes **nothing** (padding moves it by ≤ 4.2e-12 voxels; 100% of the movement was the Lee path).

## Three array-bound guards clamped at zero cost

**Three array-bound guards were clamped at the same time, at zero cost, and that is what the crop figures rest on.** The ring crop in `contour_femoral_neck` and the `r_3` restriction in `get_femoral_neck_center_lee` each **skipped** their nulling when the circle reached past the array edge (`if center[1] + c_a < mask.shape[1]`, `if center[1] - c_a > 0`) rather than clamping it, and both loops ran `range(shape[0] - 1)`, leaving the last sagittal row never nulled. All of it fires on **0 of 100** halves in the production framing, so clamping and extending the range is **zero-movement** — verified identical on all 100, torsion and endpoint, max 0.0, with no golden moving. Under a crop to the mask bounding box it is the difference between **3 of 96** and **86 of 96** exact. (The dead `x` / `y` lists in the `r_3` loop went with it: appended to, never read.)

## The layer choice was the second crop residual

**The layer choice was the crop residual, and it is now closed too (2026-11-06).** Translation was already at 100/100 and, given the same layer, the notch frame, the notch cell and `a` are exact on 100/100 under a crop as well — but the layer loop itself was array-bounds dependent, and the fix is one line. Measured over the 100 Augsburg reader-study halves with the femur cropped to its own bounding box at **margin 0** (bone sitting *on* the border, the only framing in which this fires): the selected layer survived on **88 of 100**, `find_contours`'s count flipped on **12** (1 → 2 on nine halves, 1 → 3 on three) and the `2 · r` circle test flipped on **0**, with the head centre and radius **bit-identical** on all 100.

**Only one of the two tests was ever responsible**, contrary to the attribution this file carried: `skimage.measure.find_contours` does not close a region reaching the array edge — it returns one *open* polyline per disjoint interval of border contact, so bone on two or three sides reads as two or three contours, the single-outline test fails and the walk runs on (7 → 8, 8 → 10, 18 → 21 twice, 18 → 19, 8 → 9, 6 → 7 twice, 6 → 8, 7 → 9 twice, 16 → 17). `points_on_circle` **could not** have been responsible and should not be "fixed" for it: it keeps a sample only if it is in bounds **and** on bone, so an out-of-bounds sample already *is* a not-bone sample, and a crop that preserves every bone voxel cannot change its verdict. The fix evaluates that one test on a `_NECK_LAYER_BORDER`-voxel zero border, which makes the layer a function of the bone alone.

## Why the layer fix is zero-movement, and the four halves it recovered

**It is zero-movement, and it recovers four halves that used to fail outright.** In the production framing the same layer is selected on **100 of 100** uncropped halves, and the Lee neck centre and the proximal axis bearing are **bit-identical to the pre-change code on all 100** (max |Δ| exactly 0.0, no resolve/fail change); `git diff tests/golden/` is empty, which matters because four Lee goldens read this path. End to end under the margin-0 crop the shipped code was measurable on 96 of 100 (four raised `RuntimeError`) and followed the crop on **86 of 96**, max error **54 voxels**; the bordered code is measurable on **100 of 100** — so the four that stopped resolving a notch were the same defect — and follows the crop on **98 of 100**, max error **1 voxel**.

**It was not 100/100, and the residual turned out to be a different mechanism from the one this file twice blamed.** The two that still moved were `PA000012` image-right and `PA000667` image-left, which both `9f41e68` and this bullet attributed to 3-D `utils.get_contour`'s `binary_erosion(border_value=0)` reporting the array border as contour.

**That attribution was wrong** (corrected 2026-11-06, see the next bullet): traced stage by stage, the head centre, the layer, the contour (4258 and 5151 voxels), `r_1`/`r_2`/`a`, `center_fn`, `r_3`, the surviving contour point set *and* the fitted slope are all identical between the uncropped and cropped arrays — only the final rounding of the reported endpoint differed. Bordering `get_contour` would in any case have been the wrong move: it feeds `get_contour_points`, which the alpha angle (`measurements/hip.py:594`) and the femoral-head sphere-fit point cloud (`hip.py:404`) also use, so it would have moved the head centre and with it every hip measurement. Quote the claim as **“invariant under translation, and under any crop that does not leave bone on the array border”**. Note also that the two figures are different quantities and must not be conflated: the LAYER index goes 88 → 100 of 100, while the end-to-end neck centre goes 86/96 → 98/100, because the second mechanism survives.

## The third crop residual: int() truncation toward zero

**The last crop residual was `int()` truncating toward zero, and it is now closed (2026-11-06).** `get_femoral_neck_center_lee` reports a point `_NECK_AXIS_REACH` (80) voxels back along the fitted neck axis from the head centre — a *synthetic far point*, not a landmark on bone, so it routinely falls outside the array. It was rounded with `int()`, which truncates **toward zero**: it rounds a positive argument down and a negative one up, so it does **not** commute with adding an integer across zero. Cropping drops `center[1]` below the axis reach, the coronal argument lands in `(-1, 0]`, and `int()` rounds it **up** to 0 where `np.floor` gives −1 and reproduces the uncropped answer. This is the hazard the "physical coordinates stay floats" convention below already records ("casting mm coordinates to `int` truncates toward zero, which makes a measurement depend on the image's position in the scanner frame") — biting an **index** coordinate, which is why it was not looked for there. The fix is `np.floor`, and it is **zero-movement**: over the 100 Augsburg reader-study halves both arguments are non-negative on all 100 in the production framing, so `int` and `floor` agree exactly there, and the Lee neck centre and proximal axis bearing are **bit-identical to the pre-change code on all 100** with an empty `tests/golden/` diff. Under the margin-0 femur-bbox crop the coronal argument falls in `(-1, 0]` on exactly those two halves, and the neck centre now follows the crop on **100 of 100**, max error **0.000 voxels** — so the Lee crop invariance is complete: 86/96 before the layer fix, 98/100 after it, 100/100 now. The sagittal argument is `-80 + center[0]` with `center` already `int16`, i.e. an exact integer, so its sign never mattered; it is floored too only so the pair reads consistently. Pinned by `tests/characterization/test_lee_endpoint_rounding.py`, whose two parametrisations fail against the pre-change code with exactly the coronal off-by-one.

## One dead expression, since repaired

**One dead expression, recorded here so it is not mistaken for the defect, and since repaired**: `utils.points_on_circle` used to end `return np.array(points) > 0`, returning a **boolean array** rather than the points it collected. Only `len(...) > 0` was ever read and `femur.py` is its only caller, so it was harmless, and it was listed here as a separate tidying item — **it was then fixed in `d980792` (2026-11-06) and the function now returns `np.array(points)`**, so this paragraph describes history and not the shipped code. The same commit is the one the "three advertised-but-broken paths" bullet above records; do not read the two as disagreeing about the current return value.

## A failure path improved on the way

**A failure path improved on the way**, untested on data because it never fires on these 100 halves: when no second dorsal point existed the old code raised `IndexError` (`indices[-1]` on an empty contour), which is **not** in the `(RuntimeError, AssertionError, ValueError)` tuple the batch scripts and `compute_torsion.py` catch — so it would have aborted a cohort run instead of writing a NaN row. It now raises `RuntimeError`.
