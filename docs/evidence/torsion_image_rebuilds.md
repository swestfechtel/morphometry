# The torsion image: rebuild records

Every rebuild of `swestfechtel/torsion` since the pins went in, with what moved and how it was
verified. Moved verbatim out of `CLAUDE.md`, which keeps the rebuild rule, the pin rationale, the
two fixtures to verify against, the methodological lesson and the currently published digest.

The lesson worth carrying forward, because it cost a wrong write-up once: **the recorded sha is
not evidence of what an image contains — run it, or hash its `/app/morphometry`.** A `grep` for
prose in the source tree is not evidence either.

**A note on cross-references.** These paragraphs were written inside `CLAUDE.md`, so an
"above", "below" or "recorded here" may point at a bullet that stayed there rather than at
something on this page. Nothing was reworded, which is the point; the file it came from is
`CLAUDE.md` and the two are meant to be read together.

## The four rebuilds: 6d7be91, 7ccaf44, 2d1fc91 and the 1bd8980 staleness window

**Rebuilt again at `6d7be91` (2026-11-06), and this one is the easy case: purely additive, no measurement moved.** Old image preserved as `swestfechtel/torsion:pre-6d7be91` per the convention below; new local image `212ea8e1b3c0`. Verified the two ways this file requires. (a) Against the venv: the rebuild's `results.json`, `landmarks.json` **and** `errors.json` are **byte-identical** to running `morphometry/docker/compute_torsion.py` in the venv on the PA000001 reader-study fixture. (b) Old against new on the same fixture:

**6 keys added, 0 removed, 0 changed** — the two Lee QC flag keys and the four condylar ones, with *every* shared key bit-identical, including all four femoral and both tibial torsion angles. So unlike the `1bd8980` rebuild (which moved `femoral_torsion_{left,right}` by ±1.4°), **nothing a consumer reads changed** and there is no do-not-pool burden. The 38-package closure is unchanged: `pip freeze` in the image matches `morphometry/requirements.txt`'s 38 pins exactly (comments aside).

**Not pushed to Docker Hub** — publishing is the user's call, and the previous push was done by them. One caveat on the evidence: the `murphy_axis_short` unit change (mm -> voxels, recorded above) is **invisible on this fixture**, because PA000001's necks are sound and the Murphy flag string is therefore `''` on both sides; it affects only flagged halves, of which this fixture has none.

**REBUILT at `7ccaf44` (2026-11-10), and the rebuild corrected a provenance error in this very bullet — including a wrong claim an earlier version of this paragraph made.** Outgoing image preserved as **`swestfechtel/torsion:pre-7ccaf44`** per the convention above; new local image **`75173e2cb663`**.

**The record of what the on-disk image was built from was wrong, and the image itself had to be interrogated to find out.** This bullet said the local image `212ea8e1b3c0` was the `6d7be91` build, and on that basis a first attempt here reported the image as "five commits behind" and claimed a rebuild would move the two `murphy_axis_short` strings from millimetres to voxels.

**That was a source-tree comparison presented as an image comparison.** Run for real, the preserved image emits `murphy_axis_short:6.37` and `:11.67` — the **voxel** form — so it already carried code newer than `6d7be91`. Its provenance was then pinned by copying `/app/morphometry` out of the image and hashing it against each candidate commit: `femur.py`, `hip.py`, `knee.py`, `constants.py` and `measurements/hip.py` intersect uniquely at **`8f12791`**, not `6d7be91`. So the image was rebuilt at `8f12791` and this file never recorded it, and the real staleness was **four** commits (`f97200f`, `7c3c398`, `cd2cd36`, `1bca0a3`), all of them output-neutral for this container.

**Verified four ways, and the rebuild moves nothing.** (a) The new image's `results.json`, `landmarks.json` and `errors.json` are **byte-identical** to running `morphometry/docker/compute_torsion.py` in the venv at HEAD, on **both** the sound PA000001 fixture and the **flagged** PA001127 leg — the standard this bullet requires. (b) New image against the preserved one: **byte-identical on both fixtures**, every angle, every landmark and every flag string, so the four intervening commits changed no container output at all and the API was **not** serving stale numbers. (c) `pip freeze` in the image is **exactly** the 38 pins of `morphometry/requirements.txt` (comments aside). (d) `git status --short morphometry/` was empty at build time, so the image reflects HEAD and not a dirty tree.

**Still NOT pushed to Docker Hub — that remains the user's call**, as the previous push was theirs; what has changed is that the local image now matches HEAD and the publish carries a measured zero numeric risk rather than an unknown. The alpha-angle commits in that range are invisible here for a structural reason worth stating: `measurements/hip.py` is **not in this container's import closure** (it imports `measurements.femur` and `measurements.tibia` only), so the radial-position mechanism and its reverted reduction cannot reach the torsion image at all.

**This time it did not, and that was established four ways before the build, not asserted:** (i) the container's **real import closure is 13 files** (walked from `compute_torsion.py`'s AST), and **23 of those 25 commits are the `knee-cartilage-delta-maps` merge, which touches only `morphometry/cartilage/*` — entirely outside the closure**, so it cannot reach the container at all; (ii) of the two closure files that differed from HEAD, `femur.py` is **AST-identical with docstrings stripped** (`ea688b3` was prose only) and `hip.py` had **exactly one** changed definition, `get_femoral_head_center_ct`; (iii) a call graph walked from the container's eight entry points reaches **72** functions and `get_femoral_head_center_ct` is **not** among them — **no `_ct` function is reachable at all**, the one closure call site (`femur.py:1480`) living in `_ct_proximal_landmarks()`, which the container never enters; and (iv) the **preserved** image and HEAD-in-the-venv were run on the PA000001 fixture and gave **byte-identical** `results.json`, `landmarks.json` and `errors.json`. So the pre-rebuild image was already output-equivalent to HEAD and the API was **not** serving stale numbers; the rebuild buys provenance, not correctness.

**Verified after the build the four ways this bullet requires.** (a) The new image's three JSONs are **byte-identical** to running `morphometry/docker/compute_torsion.py` in the venv at HEAD, on **both** the sound PA000001 fixture and the **flagged** PA001127 leg. (b) New against the preserved image: **byte-identical on both fixtures**, every angle, every landmark and every flag string — so the 25 commits changed no container output whatsoever. (c) `pip freeze` in the image is **exactly** the 38 pins of `morphometry/requirements.txt` (comments aside), and only the three `COPY` layers rebuilt while the dependency layer came from cache, which is the second confirmation that the closure was not re-resolved. (d) `git status --short` was empty for the whole tree at build time, so the image reflects HEAD and not a dirty tree.

**The push itself carried a fifth confirmation of the dependency closure, the same one the `1bd8980` push produced**: of the 14 layers, **only the three `COPY` layers were pushed** and the other eleven came back `Layer already exists`, so the dependency layer is byte-identical to what the registry already held rather than re-resolved — independent of the `pip freeze` check above, since it is the registry comparing content digests and not us comparing version strings. Publishing remains the user's call and this one was theirs; what it shipped is a tree matching HEAD byte for byte with a measured zero numeric change, which is the lowest-risk push recorded here.

## The 1bd8980 rebuild and the pre-fix Lee torsion it had been serving

**Rebuilt at `1bd8980` (2026-11-06), and the staleness window is worth knowing about.** The image had been left at `51ce760` while four library commits landed, so the API was serving a **pre-fix Lee femoral torsion** with nothing in the API or the UI indicating it. Measured on the PA000001 fixture, old image against the rebuild: `femoral_torsion_left` **11.643151 → 13.043961** and `femoral_torsion_right` **7.409439 → 6.025752** — the only two result keys that moved. Both Murphy angles, both `*_murphy_qc_flags` and both tibial torsions are unchanged, which is the expected signature: `9f41e68` moved only the Lee path, `1bd8980` is zero-movement, `b3e7284` is bit-identical and `8d138af`'s alpha angle is not in this closure at all. Those two figures are the `femoral_torsion_{right,left}_lee` golden moves to six decimals — note the container's keys are **patient** side where the goldens' are **image** side, so they cross over. The rebuild's `results.json` and `landmarks.json` are **byte-identical** to running `morphometry/docker/compute_torsion.py` in the venv. Two landmarks the UI draws moved: `femur.Lee.{left,right}.hip_end`, by two coronal voxels each — the neck-centre endpoint, which is what `9f41e68` re-derived. The outgoing image is kept as `swestfechtel/torsion:pre-1bd8980` (the convention `pre-51ce760` / `pre-822181b` already established), so an old number can always be reproduced rather than argued about. Published as **`swestfechtel/torsion@sha256:55ef7da9…`** (local image `c99befd0c9ce`); only the three `COPY` layers were pushed, the dependency layer already existing in the registry, which is a small confirmation that the 38-package closure is byte-identical to the previous build rather than re-resolved.

## Old-vs-new on the PA000001 fixture, across the unpinned build

**Old-vs-new, measured on the Augsburg PA000001 fixture** (hip/knee/ankle, `-m needs_augsburg`). The image built 2026-06-17 (unpinned, NumPy 2.2.6, pre-`0329273` library) against the rebuild at `822181b`: `femoral_torsion_right` 4.294 → 7.074°, `femoral_torsion_right_murphy` 14.857 → 19.434°, `femoral_torsion_left` 10.777 → 11.069°, `femoral_torsion_left_murphy` 23.451 → 26.419° (i.e. +0.29 to +4.58°, all four femoral angles), `tibial_torsion_{left,right}` unchanged to within 3 and 27 ULP. Those are the numbers the API served before the rebuild versus after.

**The unchanged tibial angle is specific to this leg and does not mean the tibial output is untouched.** PA000001 resolves its notch, so task #4 left its *angle* alone; on a leg where `find_notch` fails, task #4 moved the Augsburg tibial torsion by a median 11.23° (max 16.28°) and turned five `RuntimeError`s into values. And the tibial *landmarks* did move here — `landmarks['tibia']['left']` went `knee_start [292, 188, 21]` → `[293, 188, 21]`, `knee_end [258, 187, 21]` → `[259, 187, 21]` — which is the one-voxel flip fix; it is a uniform translation of the condylar line, which is exactly why the angle survives to a few ULP while the overlay the UI draws from `landmarks.json` shifts. The femoral landmarks moved more, including Murphy's hip end becoming continuous (`[102, 184, 11]` → `[100.507, 186.284, 10.0]`). The rebuilt image's `results.json` and `landmarks.json` are **byte-identical** to running `morphometry/docker/compute_torsion.py` in the venv, and its four femoral angles are bit-identical to the `tests/golden/femoral_torsion_*` values (note the container's keys are *patient* side, the goldens' are *image* side, so they cross over).

## Torsion image and dependency pins — full bullets (from CLAUDE.md)

*Moved verbatim from `CLAUDE.md` on 2026-11-12 when that file was cut below its size limit; `CLAUDE.md` keeps a summary and links here. Nothing below was rewritten.*

- **`swestfechtel/torsion:latest`** — built from `morphometry/Dockerfile` with entrypoint `morphometry/docker/compute_torsion.py`. Pure-Python torsion computation from segmentation masks; no GPU needed. **It carries a copy of the library, so it must be rebuilt after every landmark / measurement change in `morphometry/` — otherwise the API keeps serving the numbers of whatever commit the image was last built from, with nothing in the API or the UI indicating it.** Its dependencies are pinned in `morphometry/requirements.txt`, which the Dockerfile `COPY`s and installs with `--no-deps` (the file is the complete closure, so re-resolving could only add something unpinned) followed by `pip check`; see Dependencies below. The base image is pinned to **`python:3.10.16-bookworm`**, the venv's exact interpreter — the floating `python:3.10` it replaced had already drifted to 3.10.22 on Debian 13 / GCC 14.2.0 against the venv's 3.10.16, so the 38 package pins alone did not make the two the same code path below the wheels. **Residual, not closed**: the venv's own interpreter was built with GCC 11.2.0 against glibc 2.43, the image's with GCC 12.2.0 against glibc 2.36, and the base is pinned by tag rather than digest. It did not bite on PA000001 (the rebuild on the pinned base is byte-identical to the one on trixie), partly because `numpy==1.26.4` is the same OpenBLAS `DYNAMIC_ARCH` manylinux wheel either way and the same CPU dispatches the same kernels — neither is guaranteed on another host. The image also installs `libgl1 libxrender1`, because `measurements/hip.py` annotates `plot: plt.Axes | pv.Plotter | bool` and that annotation is evaluated at def time, so importing the measurements pulls in `pyvista.plotting` → `vtkmodules` → `libGL`. Nothing in the image renders; without them `pyvista==0.44.1` / `vtk==9.3.1` fails at import and the container exits before measuring anything (the old unpinned builds happened to resolve a pyvista/vtk pair that did not need them). Keep that list minimal: `objdump -p` over every `.so` in site-packages gives exactly three system X/GL libraries as `NEEDED` — `libGL.so.1`, `libX11.so.6`, `libXrender.so.1` — plus hash-suffixed copies vtk's wheel vendors itself (`libXau`, `libXcursor`, `libXfixes`, `libxcb`, which read as "not found" under a bare `ldd` and resolve through the wheel's RPATH), and **nothing** from glib, gobject, gthread, libXext, libSM or libICE. So the `libglib2.0-0 libxext6` this line once also carried were dead weight — and on Debian 13 `libglib2.0-0` exists only as a `Provides` alias of `libglib2.0-0t64`, a name a later base can drop and break the build with. `libxrender1` is *not* transitively pulled by `libgl1` on bookworm, so it has to be named explicitly. **The rebuild records themselves — what each rebuild moved, how each was verified, and the provenance error that had to be corrected by interrogating the image — are in [`docs/evidence/torsion_image_rebuilds.md`](docs/evidence/torsion_image_rebuilds.md).**
  - **The lesson is methodological and worth keeping: the recorded sha is not evidence of what an image contains — run it, or hash its `/app/morphometry`.** A `grep` for prose is not evidence either; "in-plane voxels" appears in `femur.py`'s docstrings at `6d7be91`, which is what first made the provenance look consistent. **REBUILT at `2d1fc91` (2026-11-12), and this rebuild is the one where the staleness was proved harmless BEFORE rebuilding rather than discovered afterwards.** Outgoing image preserved as **`swestfechtel/torsion:pre-2d1fc91`** per the convention above; new local image **`ce9afeb4182a`**. The image had been left at `8f12791`/`7ccaf44` while **25** library commits landed, which by the rule above is exactly the configuration that once had the API serving a pre-fix Lee torsion. **Provenance is now exact, which is the point of having done this**: `/app/morphometry` was copied out of the built image and compared against HEAD file by file — **all 33 `.py` files identical**, the only extra entries being `Dockerfile`, `.dockerignore` and a local `__pycache__`. That closes the drift this bullet records from the `7ccaf44` rebuild, where the recorded sha was four commits wrong and the image had to be interrogated to find out. **PA001127 is the discriminating fixture and is why it is used beside PA000001**: its flags are non-empty, `murphy_axis_short:11.67` and `:6.37` (container keys are **patient** side, so they cross over to this file's image-left 6.37 and image-right 11.67) — the **voxel** form of `8f12791`, which PA000001 cannot exercise at all because its necks are sound and both flag strings are `''`. **PUSHED by the user on 2026-11-12 as `swestfechtel/torsion@sha256:bb619140abec79ceb9f22a5393884ea78105c18cf0014cf7fe2d4f7b6eabe9eb`** (local image `ce9afeb4182a`), so for the first time in this bullet's history the registry, the local image and HEAD all agree.
  - **What the pin is worth numerically**: with the library held at `822181b` and only the dependency stack swapped (pinned NumPy 1.26.4 versus an unpinned resolve to NumPy 2.2.6), the Lee and tibial angles are bit-identical but both Murphy angles drift by 5 and 24 ULP (1.8e-14 and 8.5e-14°). **It is not that Murphy uses the consensus head-centre fit and Lee does not** — `femur.py:704` resolves that fit *before* the method branch, so both methods pay for it. The difference is `femur.py:710`, `center = center.astype(np.int16)` on the Lee branch ("the Lee neck search indexes the mask with the centre"), which truncates the sub-voxel LAPACK difference away, while Murphy (`femur.py:715-717`) deliberately keeps the centre continuous. That is a stronger reason to pin, not a weaker one: the dependency stack reaches the output exactly where a landmark has stopped being truncated to an index, and recent work has been making more landmarks continuous (the Murphy neck base, both shaft axes, the CT head centre). Small here, and unbounded on a case where the fit is less well conditioned.
`morphometry/requirements.txt` is the **torsion image's** pinned set, `COPY`'d and installed by `morphometry/Dockerfile` (it replaced an unpinned `pip3 install nibabel matplotlib numpy …` line in the Dockerfile, which resolved NumPy 2 against the venv's `numpy==1.26.4` — the image and the research environment were not the same code path). It deliberately does **not** install the repo-root `requirements.txt`: the torsion image is pure-Python computation on masks and needs none of torch / nnunetv2 / TotalSegmentator / fastapi. It holds the ten direct dependencies of the real import closure of `morphometry/docker/compute_torsion.py` — `nibabel`, `numpy`, `scipy`, `SimpleITK`, `pydicom`, `scikit-image`, `scikit-learn`, `matplotlib`, `pandas`, `pyvista` — plus their own 28-package transitive closure (`vtk`, `joblib`, `pillow`, `tifffile`, … ), each at exactly the version the repo-root `requirements.txt` holds. Every version in the two files must stay equal; that equality is the point of the file. Because it is the *complete* closure it is installed `--no-deps`, so a package missing from it fails the build instead of being silently resolved unpinned; `pip check` runs in the same layer, and `pip freeze` in the built image is exactly these 38 lines. `Deprecated` was in the old unpinned list and is **dropped**: nothing in the repo imports it and no installed distribution requires it. `scikit-learn` is **not** droppable despite the cartilage/knee rewrites — `hip.py` still imports `KMeans`/`PCA` and `knee.py` `PCA`, both inside the torsion closure; nor are `pandas` (a `pd.Series` in `hip.py`'s subchondral statistics) or `pyvista` (`pv.SolidSphere`/`pv.Sphere` neck-centre shell sampling), which are reached through module-level imports of `morphometry.hip` even when the torsion path never calls them.
