# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The repo has four loosely-coupled parts; the three Python parts share a single virtualenv and the `morphometry` package, and `frontend/` is a self-contained Node/Next.js app:

- `morphometry/` — the analysis library, layered as an acyclic dependency graph:
  - **`morphometry/measurements/`** — all public `calculate_*` measurement functions, one submodule per region (`hip.py`, `femur.py`, `knee.py`, `tibia.py`, `ankle.py`, `whole_leg.py`, `cartilage.py`). This is the public surface (re-exported from `morphometry.measurements`). Import measurements from here, e.g. `from morphometry.measurements.femur import calculate_femoral_torsion`.
  - **Region modules** at the package root (`hip.py`, `knee.py`, `ankle.py`, `femur.py`, `tibia.py`, `whole_leg.py`, `cartilage/`) hold the landmark / reference-line helpers (`get_*`) that the measurements build on. They must NOT import from `measurements/`.
  - **Leaf infrastructure**: `image_io.py` (the `Image` / `Segmentation` wrapper every function operates through), `geometry.py` (shared pure helpers: `fold_to_acute`/`fold_to_obtuse`, `split_left_right`, `slice_centroid_to_point`, `mirror_sagittal_coordinate`, `signed_axial_angle`, `mirror_index_x`, `order_condylar_points`), `constants.py` (modality-scoped `SegmentationLabels` + tunable thresholds), `utils.py`, `bresenham.py`. These import no region/measurement code.
  - Dependency direction (enforced by `tests/test_import_graph.py`): `measurements/* → region get_* → geometry/utils/constants/image_io/bresenham`.
  - MRI vs CT: torsion / CCD / neck-center / bone-length have separate `_ct` functions (modality differs in landmark acquisition); the acetabulum / CEA / subchondral / offset family take a `ct=` flag. Shared `_core` helpers isolate the modality differences.
  - **Whole hip bone vs acetabulum**: `calculate_center_edge_angle` / `calculate_acetabular_anteversion` were written for masks that label the acetabulum separately (MRI/NaKo, isotropic). Whole-leg CT label maps have one label for the entire hip bone, so pass `acetabulum_radius_factor` (~1.4) to route them through `get_acetabular_surface` (in `hip.py`), which keeps only the bone *facing* the femoral head — per ray out of the head centre, the first bone voxel — so the iliac wing is shadowed rather than mistaken for the acetabular rim. That flag also switches CEA's angle into millimetres: the default index-space arithmetic is only valid for isotropic voxels, and on 0.8×0.8×3.0 mm CT it inflates a 25° angle to ~60°. Default `0` keeps the legacy behaviour, so the MRI goldens are untouched.
  - Torsion `calculate_*` return only the angle; landmarks come from `get_femoral_torsion_landmarks` / `get_tibial_torsion_landmarks`. Measurement functions never change their return arity based on `plot` — pass a matplotlib `Axes` / PyVista `Plotter` to `plot=` to draw overlays.
- `api/` — a FastAPI service (`api/main.py`) that ingests DICOM uploads or Orthanc callbacks, stores examination metadata in SQLite + images as `.nii.gz` files (`api/db`, `api/storage`), and dispatches model jobs to a **Redis/RQ worker** (`api/tasks`) that shells out to the docker images (see below). Layered: `routers` → `ingest`/`serializers`/`deps` → `db`/`storage`/`tasks` → `settings`/`runtime`. Config is env-driven via `api/settings.py` (`MORPH_API_*` / `.env`). `api/examination.py` is legacy, kept only for `scripts/migrate_pickles.py`. Torsion uploads are **two-phase**: `POST /upload/torsion/series` enumerates the DICOM series in a whole examination folder (grouping by SeriesInstanceUID, discarding junk, rendering previews) into a `pending_selection` examination; the user picks a series (whole-leg → auto-split, or three hip/knee/ankle series) via `POST /upload/torsion/select`, which materializes it and auto-starts the full pipeline. A whole-leg series is frequently a **gapped 3-station acquisition** (hip/knee/ankle slabs); `api/ingest/dicom.py::_detect_slabs` splits it at the position gaps and converts each slab on its own so SimpleITK doesn't average the gaps into a ~2×-inflated z-spacing (which would silently corrupt all superior-inferior distances) — see `api/README.md` "Multi-slab acquisitions". **Auth** (`api/auth/`): username/password login (`POST /auth/login` → signed Bearer token, argon2 hashes) coexisting with `X-API-Key` for machine clients; users are managed with `python -m api.users`. See `api/README.md`.
- `scripts/` — one-off batch processing scripts (`process_augsburg_*.py`, `process_nako*.py`, `combine_series.py`, etc.). Each script is self-contained and typically prepends `sys.path.append('/home/simon/Work/morphometry')` and hard-codes absolute data paths (e.g. `/home/simon/Data/...`); update paths when running elsewhere. A few are proper `argparse` CLIs — e.g. `compute_knee_cartilage_thickness.py -i <seg.nii.gz ...|dir> [--femur-label 3 --tibia-label 4 --tibia-bone-label 2 --laterality-table lat.csv --method knn -o summary.csv --dump-json maps.json --visualize both --screenshot <dir> --html <dir>]` computes per-subregion knee cartilage thickness and optionally renders the 3D segment/heatmap views (via `plot_knee_segments`/`plot_knee_thickness`) as PNGs (`--screenshot`) and/or self-contained interactive HTML (`--html`). `-i` accepts multiple files and/or directories (searched recursively for `*.nii`/`*.nii.gz`); multiple inputs batch into one combined CSV (leading `subject` column) + one combined JSON (keyed by subject). All visualisation files land flat in the `--screenshot`/`--html` dirs named `<subject>_knee_<view>.<ext>`. Output paths ending without an extension are treated as directories (`summary.csv`/`thickness.json` written inside). `process_nmdid.py -i <seg.nii.gz ...|dir> -o <dir> [--shard I/N --workers N --cohort-status cohort_status.csv --verdict usable review --limit N --overwrite --merge]` batches the whole-leg **CT** measurements (femoral torsion/Murphy, tibial torsion, CCD, femur & tibia length, femoral offset, mechanical axis deviation, HKA, center-edge angle, acetabular version) over the NMDID cohort, one CSV row per (case, image side). Built for SLURM: `--shard` (or `SLURM_ARRAY_TASK_ID` / `SLURM_ARRAY_TASK_COUNT`, see `process_nmdid.sbatch`) strides the cohort across job-array tasks that each fan out over their node's CPUs into their own `shard_XXX.csv`; `--merge` concatenates them. Rows are flushed per case, so an interrupted run resumes. Because these are whole-*body* scans, `clean_leg` drops the mislabelled arm bones (non-pelvis label components lying entirely above the hip bone) and the spine/rib fragments in the pelvis label; segmentations that are damaged in ways it will not silently repair are reported in a `qc_flags` column instead.
 - `process_nako_large.py --chunk N [--input-root <dir> --output-dir <dir> --workers N --overwrite]` measures one chunk of the NaKo cohort (`<input-root>/chunk_N_segmentations`, `.nii.gz` only — the chunk dirs also hold three nnU-Net json files) into `results_chunk_N.csv`, in the original cohort-table layout (one row per Patient and *patient* Side; image-left half = patient right), plus `results_chunk_N.meta.json` (git commit, dirty flag, date, args). Each finished case is flushed to `results_chunk_N.partial.csv`, so a killed task resumes on resubmission (a case torn mid-write, or a partial with no complete row, is dropped and recomputed). A case that cannot be loaded is not flushed but retried once at the end of the run, then written as all-NaN rows; more than `--max-load-fail-frac` (0.01) load failures in a chunk fail the run without finalising (a broken mount, not bad files). A worker that dies hard raises `BrokenProcessPool` rather than hanging and saves the cases in flight to `results_chunk_N.suspects.json`; the next run measures each suspect alone first and writes one that still kills its worker as all-NaN rows. Both kinds of NaN case are listed in the meta file (`load_failed`, `crashed`). When every case is in, the rows are sorted into `results_chunk_N.csv` and the partial file removed. A finished chunk CSV is refused without `--overwrite` (which starts the chunk afresh). `--output-dir <dir> --merge [--expected-chunks 20]` concatenates the chunks in numeric order into `<dir>/results.csv`, refusing missing, unfinished or out-of-range chunks and duplicate (Patient, Side) rows. `process_nako_large.sbatch` is the SLURM array (tasks 0-19, one chunk each, 32 CPUs) writing to a fresh `~/Data/nako/rerun_<short sha>`; it refuses a dirty checkout, and the checkout must not change until the array has finished. Acetabular anteversion now runs with `isotropic=True` like every other NaKo measurement (before: `isotropic=False`, the consensus head-centre fit). Cohort tables from before this change also hold empty rows named after the json files (`dataset`, `plans`, `predict_from_raw_data_args`); the cohort is 30,407 cases.
 - `analyse_thinnest_point_flexion.py -i <dir> [--tibia-bone-label 2 -o <dir> --screenshot/--html <dir> --visualize]` groups `K<subject>_<angle>_<load>.nii.gz` segmentations by `(subject, load)` and tests whether the thinnest point migrates posteriorly with flexion — measured as the thinnest point's arc-length fraction along the femoral articular surface (frame-invariant across the separately-acquired flexion scans), summarised per series (Spearman ρ + slope) and cohort-wide (binomial sign test). Everything is done per **compartment** — `both` (whole knee), `left`, `right`: `detail.csv` is long format (exactly one row per parsed scan × compartment, `compartment` column after `angle`), series and `summary.csv` (insufficient series kept with NaN stats) are keyed by `(subject, load, compartment)`, and the sign test is reported separately per compartment (separate, uncorrected tests; the two loads of one subject are not independent). 'left'/'right' is the PATIENT side (from the NIfTI header after LPI reorientation), not medial/lateral: patient-left is medial in a right knee and lateral in a left knee, so a per-side sign test reads as medial or lateral only if every knee in the cohort is the same side. A compartment whose search fails becomes NaN for that scan (stderr warning) without dropping the other compartments; a scan whose thickness pipeline fails is written as NaN for all three. Visualisations draw one arrow per compartment in a single scene.
- `frontend/` — the **Next.js 15 / React 19 / TypeScript** web UI for the API (Tailwind 4 + Flowbite, npm). It is the only client of the API and uses its exact contract: the `{examinations: [...]}` list envelope, base64 image/segmentation layers, and the `/examinations`, `/upload`, `/model/{segmentation,torsion}/{id}`, `/jobs/{id}` endpoints. App Router code lives under `frontend/app/`; the API base URL is `frontend/app/server_config.ts` (env `NEXT_PUBLIC_MODEL_API`, default `http://localhost:8000`). Node toolchain is independent of the Python venv. See `frontend/CLAUDE.md` for UI architecture.

## Core data flow

1. **Images** — every analysis function expects a `morphometry.image_io.Image` or `Segmentation`, which wraps either a `nibabel.Nifti1Image` or a `SimpleITK.Image`. Construct with `Image.from_nibabel(...)` / `Segmentation.from_nibabel(...)` or `Image('nibabel').read_image(path)`.
2. **Coordinate system** — masks must be placed in **LPI** orientation before measurement. Always call `seg.transform_coordinate_system()` right after loading; `remove_outliers()` is also commonly applied before measurement.
3. **Left/right splitting** — pipelines split a full-body mask at `array.shape[0] // 2` into `left_*` / `right_*` halves. Note: "left" / "right" refers to the *image* side, not the patient side. Functions take a `side='left'|'right'` argument and document this convention explicitly. Whenever a half is used as an `Image`/`Segmentation` (i.e. with geometry), split with `image_io.split_image_left_right` — never wrap `array[half:]` in the parent's affine. Its guarantee (both backends): the left half keeps the parent geometry; the right half's index `i` maps to the same physical point as the parent's `i + [half, 0, 0]`. The parent affine on the right half put every right-side physical coordinate `half * spacing_x` off (195 mm on the CT fixture). Index-space landmarks from a right half still need `+ half` on x to address the whole mask (e.g. `right_fhc_adj[0] += left_mask.shape[0]`). It shares its affine-advance with `split_ct_image`'s z-crops and the public `image_io.crop_image(source, axis, start, end)` (all via `_crop_axis`); the API's changepoint hip/knee/ankle split (`api/ingest/dicom.py::_split_volume`) uses `crop_image` too. Two left-right flips exist and are not interchangeable for physical-space code: `image_io.mirror_image_left_right` relabels indices (mirrored index `i` ↦ parent `n-1-i`, every voxel keeps its physical location — a left leg stays a left leg physically), while `image_io.reflect_image_left_right` reverses the voxels but keeps the geometry, producing the physical *mirror twin* (a left femur becomes a right femur in index and physical space). `geometry.split_left_right` is the geometry-free array split.
   **Femoral torsion is mirror-equivariant by construction.** The proximal-femur and knee landmark searches are written for a left image half; a right half is measured as the reflection of a left one: `get_proximal_reference_line{,_ct}(side='right')` and `measurements/femur.py::_mri_torsion` / `_ct_torsion` reflect the right half (`reflect_image_left_right`, knee arrays `[::-1]`), run the left-side code, compose the angle there with the left conventions, and map landmarks back with `x -> n-1-x` (`geometry.mirror_index_x`, with `geometry.order_condylar_points` restoring the reported endpoint order). A mirrored left half through `side='right'` therefore gives exactly the left result (pinned by `tests/characterization/test_femoral_torsion_equivariance.py`, MRI Lee/Murphy + CT, stage by stage; pure composition in `tests/unit/test_torsion_angle_equivariance.py`). This replaced separate right-side branches that were systematically different: a flip off by one voxel (`c + (n//2-c)*2` instead of `n-1-c`), a head trim that scaled an index and so was not the mirror of the left trim, `astype(int16)` truncation of the head centre (floor is not mirror-consistent) and an asymmetric knee condylar search. `calculate_anteversion` shares the reference line, so its right side is equivariant too.
   **The CCD and the tibial torsion are too, the same way.** `measurements/hip.py::calculate_ccd` measures a right image half as the *mirror* of a left one (`mirror_image_left_right` of the hip and knee images, left-side code) and `calculate_ccd_ct` as the *reflection* (`reflect_image_left_right`); the two are not interchangeable here. The MRI CCD composes its angle from physical coordinates spanning two images whose affines have different origins, so it needs an operation that keeps every voxel's physical position — a reflection mirrors each image about its own array centre, and those are the same world plane only if the two images share an index-to-world x map (origin *and* direction), which separately acquired hip and knee series do not: equal array widths are not sufficient, and on Augsburg, where both halves are 192 wide, reflecting each about its own centre still costs a median 1.22° (5.7° on PA000031, whose hip and knee origins are 13.5 mm apart) — whereas the CT landmark code reads physical directions (which physical x is lateral) and so needs the mirror-twin leg. `measurements/tibia.py::_tibial_torsion_points` reflects the knee and ankle arrays (`[::-1]`), composes with the left conventions and maps the landmarks back, so `get_tibial_torsion_landmarks` now does depend on `side`. Pinned by `tests/characterization/test_ccd_tibial_equivariance.py` (both probes, MRI + CT); its MRI CCD probe has to reflect the hip and knee images about one *common* world plane rather than each about its own centre, which is a property of the probe, not of the measurement. Measured over 50 Augsburg cases, 60 NaKo hips and the 46 NMDID verification legs, the two sides previously disagreed by a median 0.16–0.23° (MRI CCD, max 0.70), 0.21–0.32° (NaKo isotropic hip-only CCD, max 1.00), 0.85–1.02° (CT CCD, max 3.14), 0.8–1.1° (Augsburg tibial torsion) and 1.7° (CT tibial torsion), and now agree exactly; every left-side value is bit-identical. Quote the tibial figures partitioned by notch status, never as a bare max — the tail belongs to the `rotate_tibia` fallback, not to the side dependence. Augsburg (94 half-measurements): notch found in both frames, n=87, median 0.82°, max 3.85°; notch missing in at least one, n=7 (7.4%), median 2.63°, max 25.05° (PA000032 right). NMDID CT (92 half-measurements, 86 resolved): notch found in both, only 34% of legs, n=30, median 0.61°, max 3.28°; notch missing, n=47, median 3.07°, max 126.73° — and that 126.73° is the single case where the two folded answers landed on opposite sides of the (−90, 90] seam, not a measurement moving by 127°. Making such a leg equivariant makes the two sides *agree*; it does not make either right. The CCD disagreement came from the femoral *neck* centre (the `pv.SolidSphere` shell sampling is not symmetric about the head centre), not from the head centre or the shaft axis — the shaft centroids' former `int()` truncation shifted both endpoints by the same voxel (when both centroids were fractional) and so cancelled in the shaft vector. The endpoints are now unrounded (see the shaft-axis paragraph below), which moved the CCD itself by a median 0.08° on the 50 Augsburg reader-study hips (max 0.28°, both sides) and 0.22° on the NaKo projected CCD (max 0.57°).
   NOT (yet) equivariant, left untouched: `get_femoral_head_center(side='right')` (non-isotropic path; the isotropic one is fixed, see the next paragraph) and `get_femoral_head_center_ct(side='right')` themselves — so every measurement that calls them directly rather than through a reflection (`calculate_acetabular_depth`, `calculate_min_distance_between_femoral_head_and_acetabulum`, `calculate_subchondral_distance_ray_tracing{,_ct}`, `calculate_femoral_offset{,_projected}`, `calculate_center_edge_angle`, `calculate_acetabular_anteversion`, and `whole_leg`'s `calculate_mechanical_axis_deviation` / `calculate_hip_knee_ankle_angle`) — plus `calculate_knee_rotation_angle`, whose own `side` branch flips the two posterior-condyle orientations. Note the consequence for a right leg: since the CCD now reaches its head centre through a reflection while those others still call `get_femoral_head_center{,_ct}(side='right')` directly, one `process_nmdid.py` row derives the CT head centre two ways (worth 0.71° of CCD on the `case-105094` fixture). That is the price of fixing the CCD alone and goes away with the head centre itself. **Do not pool old and new right-side rows**: every NMDID CSV produced before this change carries the old right-side CT CCD (it rose by a median +0.80°, range -0.88 to +3.14 over the 46 verification legs) and the old right-side tibial torsion, the same way every CSV before 82f2221 carries the biased CT femoral offset. Don't reintroduce `side == 'right'` branches into the torsion, CCD or tibial-torsion landmark code — add left-side logic and let the reflection handle the right.
   **The NaKo centre-edge angle and the isotropic head centre are side-symmetric too.** `calculate_center_edge_angle` used a lateral-edge search band of 1.5 head radii on the image-left half and 1.1 on the image-right one (an ad-hoc edit, bd385f5); it is now one `C.CEA_UPPER_MARGIN_FACTOR` for both sides — first 1.5, then 1.1 (see the end of this paragraph). Separately, the isotropic path of `get_femoral_head_center` built its lateral cutoff from `int()` of the top-slice centroid, and floor does not commute with `x -> n-1-x`, so the image-left centre sat ~0.4 voxel more lateral than the mirror of the image-right one and read the CEA ~1.1° lower on the same hip. The cutoff now uses the unrounded centroid, and the column walk the nearest column with half-voxel ties broken towards medial (`floor(x+0.5)` left, `ceil(x-0.5)` right; plain `np.rint` rounds ties to even, which does not mirror). The anterior cutoff and the consensus/Augsburg path keep `int()` and are bit-identical. Over the 60 NaKo reference hips the reflected CEA now reproduces the swapped original on all 60 (to 3e-11°). Before, it matched on none: median 1.39°, max 12.8° with the old per-side factors (median 1.10°, max 2.40° from the head centre alone, factors equalised). The patient-left minus patient-right CEA went from +2.41° (p=3e-5) to -0.64° (p=0.22); about 1.9° of the old difference came from the factors and 1.1° from the head centre (head-centre fix alone: +1.29°, p=0.016). Pinned by `tests/unit/test_femoral_head_isotropic_equivariance.py` and `tests/characterization/test_cea_equivariance.py`. **The factor was then lowered to 1.1, and that value was chosen against the 60 NaKo reader cases — calibration on the evaluation set, so those cases no longer give an unbiased estimate of CE agreement.** The CEA under-reads both readers there, and agreement improves monotonically as the factor drops (1.5 -> 1.1: ICC2 vs MH right/left 0.37/0.39 -> 0.48/0.53, vs TH 0.50/0.47 -> 0.62/0.62; signed bias MH -6.0/-6.5 -> -4.8/-4.6°, TH -2.5/-4.6 -> -1.3/-2.7°). Both sides still share one value, so the measurement stays mirror-symmetric (60/60 exact at 1.1); patient L−R is +0.12° (p=0.8). Over the 60 hips the change moved 46 of 120 CE values (mean over all 120 +1.55°, over the 46 that moved +4.04°, max 11.8°); on the 46 NMDID CT verification cases the CEA is identical at 1.1 and 1.5. **Do not pool NaKo CE rows produced at 1.5 with rows at 1.1.** **Do not pool CEA rows produced before and after this change.** NaKo: CEA (against the original 1.5/1.1 code, at the final factor 1.1: median per-hip change +0.95° patient-right, -0.14° patient-left, max 9.76°; the intermediate 1.5 gave +0.67° / -0.67°, max 11.9°), alpha angle (median |change| 0.36°, max 4.9°), projected femoral offset (0.19 mm, max 1.1 mm), isotropic CCD (0.25°, max 1.1°) and femoral anteversion (0.05°, max 1.3°) all moved; `process_nako_large.py`'s acetabular anteversion (`isotropic=False`) did not. The single factor also applies to the CT and non-isotropic MRI CEA: against the original code their image-right band is unchanged at 1.1 radii and their image-left band went from 1.5 to 1.1. On the 46 NMDID verification cases (`process_nmdid.py` settings) the CEA is identical at 1.1 and 1.5, but that is not a guarantee for the rest of the cohort, and no non-isotropic MRI CEA was measured. `calculate_alpha_angle` was already equivariant before this change, on every path: it reverses a right half (`mask[::-1]`) and runs the left-side code (120/120 NaKo halves exact before and after).
   **The MRI femoral shaft axis and the NaKo femoral offset are side-symmetric too.** `hip.py::get_femoral_shaft_axis` truncated both of its slice centroids with `int()`, so the shaft axis of a reflected hip sat one voxel from the mirror of the original's, and `calculate_femoral_offset_projected` read the same NaKo hip a median 0.99 mm (max 1.00) differently depending on its image side, with the head centre already mirror-exact. The endpoints index no array and are now returned unrounded (float voxel indices). All 118 measurable NaKo halves now agree with their reflection exactly (0/118 before), and the patient-left minus patient-right offset went from -1.13 mm (p=0.04) to -0.23 mm (p=0.68). Pinned by `tests/unit/test_femoral_shaft_axis_equivariance.py` and `tests/characterization/test_femoral_offset_equivariance.py`. **Do not pool femoral offset or CCD rows produced before and after this change**: the NaKo projected offset moved by a median -0.43 mm on the image-left half and +0.42 mm on the image-right half (max 0.95 mm), the NaKo projected CCD by a median 0.22° (max 0.57°), the Augsburg MRI CCD by a median 0.08° (max 0.28°). CT is unaffected (`get_femoral_shaft_axis_ct` already returned floats). On the non-isotropic path the femoral offset still calls `get_femoral_head_center(side='right')` directly and is therefore not equivariant; separately, `calculate_femoral_offset` with a `knee_image` combines a shaft start in the knee's index space with a head centre in the hip's (no production caller passes a knee).
   **Femoral torsion composition is rotation-invariant and signed.** `measurements/femur.py::_femoral_torsion_angle` returns the signed axial-plane angle from the (undirected) posterior condylar line `c` to the neck axis `n = hip_start - hip_end` (neck point -> head centre), folded into (-90, 90]. In LPI a left image half is a patient-right femur (medial = +x, anterior = -y), so `AT = atan2(-(c_x n_y - c_y n_x), c . n)`; `side='right'` negates the x components. **Positive = antetorsion relative to the landmarks, negative = retrotorsion.** It is computed in index space (assumes equal in-plane x/y spacing). The former fold-to-acute composition equalled `sign(neck image angle) * AT`, i.e. returned `-AT` whenever the head lay level with or posterior to the neck point in the image. The Augsburg readers never recorded a negative AT, so they cannot adjudicate retrotorsion. Evidence (reader-study and NMDID before/after, synthetic derivation) is in the commit message; pinned by `tests/unit/test_femoral_torsion_composition.py` and the real flip cases in `tests/characterization/test_torsion_head_posterior.py`. **Tibial torsion** (`measurements/tibia.py::_tibial_torsion_angle`) uses the same helper, `geometry.signed_axial_angle` (medial -> anterior is the same rotation sense as lateral -> posterior): the signed angle from the (undirected) posterior tibial condylar line to the tibia -> fibula centroid line, **positive = external torsion, negative = internal, relative to the landmarks**; the former fold-and-sign composition negated it whenever the fibula centroid was level with or anterior to the tibia centroid in the image (pinned by `tests/unit/test_tibial_torsion_composition.py`). Tibial torsion is mirror-equivariant as of `_tibial_torsion_points` (see above), but its posterior condylar line is unreliable whenever `find_notch` fails: the fallback in `knee.py::get_knee_reference_line` (`rotate_tibia`) turns the section by ~150-170°, so the 'dorsal' points land on the anterior cortex. That happens on 62% of NMDID CT legs (the short plateau section in the `split_ct_image` knee crop makes the notch search fail more often; extending the crop alone does not fix it) and 7/96 Augsburg legs, and tibial torsion from such legs is wrong independently of the composition.
4. **Torsion landmarks** — `compute_torsion.py` now produces femoral landmarks nested by method: `landmarks['femur']['Lee'|'Murphy'][side]`. Tibia landmarks stay flat at `landmarks['tibia'][side]`. The REST layer (`api/serializers.py`, served via `api/routers/examinations.py`) handles both shapes.
5. **Whole-leg CT** — `morphometry/whole_leg.py` and the `*_ct` variants in `femur.py` / `hip.py` use `split_ct_image` (in `image_io.py`) to derive hip/knee/ankle sub-volumes from a single whole-leg segmentation with labels: femur=1, tibia=2, fibula=3, patella=5, hip=7 (defaults). `calculate_mikulicz_deviation` was renamed to `calculate_mechanical_axis_deviation`.

## Docker images

The API does not run inference in-process — the RQ worker invokes two external docker images built from this repo. Both are pulled/tagged as `swestfechtel/*:latest` and their tags are configured via `api/settings.py` (`MORPH_API_NNUNET_IMAGE` / `MORPH_API_TORSION_IMAGE`), used by `api/tasks/`.

- **`swestfechtel/nnunet_torsion:latest`** — built from `api/docker/nnunet_torsion/`. Runs nnUNetv2 predictions on hip/knee/ankle using the ResEncUNetXL plans (datasets 004, 006, 007) with a 5-fold ensemble. Requires CUDA (`--runtime=nvidia --gpus all`) and expects checkpoints under `api/docker/nnunet_torsion/checkpoints/{hip,knee,ankle}/` at build time. These checkpoints are gitignored; they must be present locally before `docker build`.
- **`swestfechtel/torsion:latest`** — built from `morphometry/Dockerfile` with entrypoint `morphometry/docker/compute_torsion.py`. Pure-Python torsion computation from segmentation masks; no GPU needed.

Rebuild commands (run from each Dockerfile's directory):

```bash
# nnUNet segmentation image
cd api/docker/nnunet_torsion && docker build -t swestfechtel/nnunet_torsion:latest .

# Torsion computation image (build context must be the morphometry/ package dir)
cd morphometry && docker build -t swestfechtel/torsion:latest .
```

## Running the API

The API and the model worker are separate processes sharing Redis, the SQLite DB,
and the storage dir. Copy `api/.env.example` to `api/.env` (or a repo-root `.env` —
both are loaded, `api/.env` wins) and adjust (`MORPH_API_*`: storage dir, redis/db
URLs, docker image tags, `API_KEYS`, `AUTH_REQUIRED`, `CORS_ALLOW_ORIGINS`).

```bash
# from repo root, with venv activated
redis-server                                   # broker + job state
python -m api.tasks.worker                      # RQ worker (one, on the 'gpu' queue → serializes GPU jobs)
uvicorn api.main:app --host 0.0.0.0 --port 8000 # the web app
```

The worker is the only process that loads volumes and runs docker (needs docker
socket access + the morphometry venv); the API process does not touch docker. Job
status is durable in the DB (`GET /jobs/{id}` survives restarts). Endpoints
require an `X-API-Key` header when `MORPH_API_API_KEYS` is set (`/health` is open).
Logs rotate in `api/logs/` (see `api/logging_config.py`). `api/orthanc_plugin.py`
runs **inside an Orthanc process** and forwards stored instances to
`MORPH_API_UPLOAD_URL` (default `http://localhost:8000/upload/orthanc`) with the
`MORPH_API_API_KEY` header. Migrate legacy `api/data/*.pkl` with
`python scripts/migrate_pickles.py`.

## Conventions worth preserving

- Docstrings are verbose: one-line purpose, `:param:` / `:return:` for each parameter. New public functions should follow this style (see e.g. `morphometry/measurements/hip.py::calculate_ccd`).
- Measurement functions commonly accept a `plot: bool | plt.Axes` argument — passing an `Axes` draws overlays instead of creating a new figure. Preserve this pattern when adding new measurements.
- The ray-traced subchondral femoral-head-to-acetabulum distance (`measurements/hip.py::calculate_subchondral_distance_ray_tracing{,_ct}`) aims its ray cone with `cone_axis`, which defaults to **`'superior'`** (world `+z`, via `_superior_direction`). That axis samples the weight-bearing acetabular dome in every subject, independently of the labelling scheme. The former default `'acetabulum'` (FHC → peri-acetabular centroid) is retained as opt-in legacy behaviour only: the centroid is dragged ~46° medially by the ischium/pubis in the label, so roughly half its rays cross the non-articular **acetabular fossa** — where the head contacts no bone — inflating the mean by ~1.5 mm and roughly tripling its spread (the two modes agree, 3.65–3.77 vs 3.78–3.94 mm, over the innermost 0–20° where both sample true lunate surface). Because the fixed axis no longer aims at the label, 3.5–18.5% of rays clear the lateral acetabular rim and are dropped; heavy loss is logged as a WARNING on the `morphometry` logger, thresholded by `min_ray_fraction` (0.7). `docs/illustrations/plot_subchondral_3d.py --axis` reads its default off this signature so the illustration cannot drift from the library.
- Both `extract_subregions` enforce subregion contiguity (`_remove_subregion_fragments`, keep 26-connectivity components ≥ 20% of the largest): a subregion is one anatomical patch, but the femur's `(x,y)` split can bucket a few edge voxels into a subregion disconnected from its main body. For the tibia (now nearest-tAB-triangle transfer, see below) it is only a safety net. No-op on clean scans (single-component subregions).
- **Tibial subregions follow Wirth & Eckstein 2008** (`morphometry/cartilage/tibia_regions.py::subdivide_tibia`, plan step 2; replaced the voxel-sphere/bounding-box scheme outright, no legacy switch). They are defined on the tibial subchondral bone area (tAB, `surface.py`) in world mm, so `Tibia` now needs the **tibial bone label** (`bone_label=2`; `tibia_bone_label=2` on `calculate_tibial_cartilage_thickness` / `calculate_knee_cartilage_thickness` / `calculate_thinnest_cartilage_area`; `--tibia-bone-label` on `compute_knee_cartilage_thickness.py` and `analyse_thinnest_point_flexion.py`); a missing bone label raises. Plates = the two largest edge-connected cAB components (`find_plates`; second ≥ `min_plate_ratio` 0.2 × largest, else a fallback area-weighted 2-means split of the largest — never fired on the 96 `dfg_knees`), named by **patient side from RAS world x** (smaller x = patient left; this rests on the header, as before). Other covered islands are dropped unless enclosed by a plate (median 0.15 mm², max 0.66 mm² per knee over the 94 usable knees; 15 mm² on the broken K7_90_belastet). tAB is hole-filled **per plate** (`total_subchondral_area` with only that plate's cAB covered), so the intercondylar area can never be filled even if the cartilage plates touch. Per plate: centre of gravity S and principal axes b1..b3 from the **exact area-weighted triangle second moments** (`area_moments`; the paper uses vertices), b3 = normal oriented superior, right-handed. Central (`c`) = elliptical cylinder along b3, `rho = sqrt((x/σ1)² + (y/σ2)²)` with σ1, σ2 the in-plane standard deviations (our reading of the paper's unspecified λ1/λ2: a uniform elliptical plate gives a scaled copy of its outline), level found by bisection on the exactly cut mesh to 20% (`central_fraction`) of the plate tAB ± 1e-5. Peripheral = two planes through S containing b3 at ±45° to `tc` (S→other S, projected into the plate plane): internal (`i`) faces the other plate, external (`e`) opposite, anterior/posterior (`a`/`p`) by world +y (no fibula landmark, the paper's reference). Cartilage voxels take the region of the nearest tAB triangle centroid (`TibiaSubdivision.region_codes_at`, world mm), stored per point in `Tibia.point_labels`. Transfer QC: `Tibia.transfer_qc` (`tibia_regions.transfer_qc`: median/p99/max voxel-to-tAB distance, `far_fraction` beyond `TRANSFER_FAR_MM` 6 mm) and a WARNING on the `morphometry` logger when `far_fraction` > `TRANSFER_MAX_FAR_FRACTION` (1%) — clean `dfg_knees` max 4.8 mm, K7_90_belastet 49% beyond 6 mm (max 45 mm), the only knee flagged; `classify_point` is a single lookup and `Femur.extract_central_weightbearing_zone` reads `point_labels` (femoral logic unchanged, but its CWBZ window moved with cLT/cRT). Thickness computation is unchanged (step 4). `Tibia.plot_regions()` draws the labelled tAB. On the 96 `dfg_knees` (1 failure, K11_90_belastet, broken segmentation: 1 mm voxels, tibia label fills the volume; K7_90_belastet runs but its tibial cartilage is ~¼ of the unloaded scan's) the region shares of the plate tAB are, patient-left / patient-right plate (n=94): c 20.0/20.0, e 16.9/15.9, i 15.6/14.1, a 23.8/25.0, p 23.8/25.0 % (paper MT/LT: c 20/20, e 16.0/17.7, i 15.6/17.5, a 24.2/22.6, p 24.1/22.2); belastet vs unbelastet same subject/angle: median |Δshare| 0.14 pp (max 1.3); across flexion angles within one subject/load: median SD 0.21 pp. ~3 s per knee. **Naming / laterality**: keys stay patient-side (`clt … plt` = patient-LEFT plate, `crt … prt` = patient-RIGHT; display `cLT`/`cRT`) whatever the laterality, so `find_thinnest_area`, `split_tibia_thickness_by_compartment`, plotting and the scripts are unchanged. `Tibia(laterality='left'|'right')` / `anatomical_tibia_names` / `rename_tibia_regions` give the paper's medial/lateral names (right knee: patient-left plate = MT; left knee: patient-right plate = MT) — there the `LT` means *lateral*, so `split_tibia_thickness_by_compartment` refuses any dict holding `*MT` keys. `compute_knee_cartilage_thickness.py --laterality-table CSV(subject,laterality)` adds an `anatomical_subregion` CSV column. **Do not pool tibial (or femoral CWBZ-derived) subregion rows produced before and after this change**: K1_0_unbelastet knn `clt` 1.885 -> 1.800 mm, `crt` 1.414 -> 1.311, `elt` 1.208 -> 1.370, `plt` 1.984 -> 1.729, `irt` voxels 916 -> 590; femoral `iclf` 2.331 -> 2.428, `ecrf` 1.265 -> 1.399, `right_anterior_zone` 2.414 -> 2.538 (the femoral zones move because their A-P window is cLT/cRT's extent). The voxel-sphere central region of 60425aa (and `calculate_ellipse`, `get_plate_corners`, the KMeans/BFS plate split, `tests/unit/test_tibia_central_region.py`) is gone; pinned now by `tests/unit/test_tibia_regions.py` (20% ± 1e-4, circular plate → four 20% wedges, invariance under 20° axial rotation / 7° slope / anisotropic + oblique sampling / SimpleITK, mirror swaps plates, enclosed intercondylar area not filled, denuded hole filled).
- `Tibia`/`Femur` clean their extracted cartilage mask before any processing (`_remove_mask_outliers`, `outlier_ratio=0.1` ctor arg): per-label 26-connectivity components smaller than the ratio of the total cartilage volume are dropped, removing mislabelled blobs / detached clusters that otherwise corrupt the Delaunay meshes. Legit cartilage (femoral horseshoe, the two tibial plateaus) is far larger than the threshold and retained; pass `outlier_ratio=0` to disable. This benefits every consumer (thickness, thinnest-area, the scripts, the API).
- `find_thinnest_area` (re-exported; wrapper `calculate_thinnest_cartilage_area`) locates the thinnest *area* of the tibiofemoral cartilage robustly: it sums the tibial+femoral thickness maps over their overlapping axial `(x,y)` coords, rasterises to a dense grid, NaN-aware median-smooths (kernel `k` derived from `neighbourhood_mm`/in-plane spacing, forced odd) to reject single-voxel outliers, argmins for the neighbourhood centre, then refines to the actual thinnest voxel within a radius disc. Returns `{point, center, center_thickness, combined_thickness, tibial_thickness, femoral_thickness, kernel_size}` (2D voxel indices — z is discarded by the thickness maps; `center_thickness` is the robust smoothed value, `combined_thickness` the raw value at `point`). `plot_thinnest_point` (re-exported; also `calculate_thinnest_cartilage_area(..., plot=pv.Plotter)`) renders the cartilage in 3D (`base='thickness'` heatmap or `base='segments'` voxels) and points a red arrow at the thinnest point — its 3D depth is recovered as the femur/tibia contact-surface midpoint at that `(x,y)` column (`_thinnest_point_physical`). Given a `{label: result}` dict instead of a single result, it draws one labelled arrow per entry (`left` red, `right` blue, `both` black; `None` entries skipped).
- **Per-compartment thinnest area**: `find_thinnest_area_by_compartment` (re-exported; also `calculate_thinnest_cartilage_area(..., by_compartment=True)`) returns `{'left': result, 'right': result}` keyed by **patient** side, each with exactly the `find_thinnest_area` fields. `split_tibia_thickness_by_compartment` partitions the tibial thickness dict by key suffix (case-insensitive; `*LT` → left, `*RT` → right; unknown keys raise), and `find_thinnest_area` runs on each subset against the *full* femoral map — the overlap restriction confines each search to its plateau, so a globally thinner other side cannot win and smoothing never crosses the notch. An empty / non-overlapping side raises a `ValueError` naming it. Side mapping: `tibia_regions.find_plates` names the plate with the smaller RAS world x patient-left (checked against the affine on K1_0_belastet: after LPI `affine[0,0] < 0`, i.e. +index x → patient left), so it rests on the NIfTI header being correct. A dict re-keyed with medial/lateral names (`*MT` keys) is refused.
- Femoral central weight-bearing zone (CWBZ) **and posterior-zone** extraction restrict to the tibia-facing superior-inferior cluster (`_restrict_to_contact_cluster`): the A-P/L-R window from the tibial plateau alone would, at high knee flexion, also capture the anterior trochlea folded into the same A-P range, so only the S-I cluster nearest the tibial contact (CWBZ: tibial-contact z; posterior zone: CWBZ mean z) is kept. The split uses a spacing-scaled **absolute** S-I gap (`Femur._si_gap()` ≈ 1.5 mm in voxels), not a span-relative one — a distant fold inflates the span and would push a relative threshold above the real (small) fold-vs-contact valley. The anterior zone is left unrestricted (it genuinely is the trochlea). Preserve this when touching `extract_central_weightbearing_zone` / `extract_anterior_posterior_zones`.
- Knee cartilage thickness has 3D visualisation (`morphometry/cartilage/knee.py`): `Tibia`/`Femur` each expose `plot_segments()` (raw subregion voxels as distinctly-coloured cube glyphs — the `SEGMENT_COLORS`/`*_SUBREGIONS` tables) and `plot_thickness(thicknesses)` (articular surface as a thickness heatmap with a shared colour bar). `plot_knee_segments`/`plot_knee_thickness` render both bones in one PyVista scene (re-exported from `measurements.cartilage`); the `calculate_*_cartilage_thickness` wrappers take `plot: bool | pv.Plotter` to draw the heatmap. All accept an optional `plotter=` and only `.show()` when they created it. Femoral posterior zones reconstruct their surface with a y/z swap to match how `calculate_thickness` extracted them.
- `morphometry/cartilage/surface.py` is the shared bone-surface geometry for the Wirth & Eckstein 2008 subregions (`docs/wirth_eckstein_2008_plan.md` step 1; used by `tibia_regions.py`). `bone_surface_mesh` = marching cubes on the (largest-component) bone label in index space, mapped to **world mm, RAS frame for both backends** through the full index-to-world matrix (`index_to_world_affine`; SimpleITK's LPS is converted, so anatomical directions in world coordinates do not depend on the loader; winding fixed for reflecting directions, outward normals), windowed-sinc smoothed (`smooth_taubin`, 20 it., pass band 0.1: sphere area within 1%, surface moved ~0.02 mm). Where the bone touches the array border (FOV cut through the shafts) the mask is extended by replicated slices and the smoothed surface is cut **exactly** at the outer voxel boundary, so the mesh is *open* there with no artificial cap. `cartilage_coverage` (cAB) = triangle centroid within `tolerance_mm` of a voxel centre of that bone's cartilage label (KD-tree, world mm); default `0.6 ×` voxel diagonal (0.52 mm on `dfg_knees`) = the half diagonal a face-adjacent cartilage voxel can be away plus 20%. It is an empirical knee point (K1_0_belastet tibial cAB 1681/1931/2000/2024/2099 mm² at 0.40/0.44/0.48/0.52/0.75 mm: tighter riddles cAB with pinholes, looser keeps growing it along the rim). Because the distance test also reaches sideways past the cartilage edge, tAB is ~1-1.6% larger than with a normal probe (label 0.4 mm out along the outward normal: tibia 2027 vs 1995, femur 4707 vs 4660 mm²) — the documented alternative. Only the given label counts, so the other bone's cartilage never covers this bone. `total_subchondral_area` (tAB) = cAB + edge-connected uncovered components that do not touch the open (FOV) boundary and are smaller than `max_hole_fraction` (0.5) × cAB area — size is what separates holes from the non-articular rest of a bone that does not reach the FOV (e.g. the femur at 90° flexion). Denuded bone at the *rim* is not enclosed and not recovered; the rule is not plate-aware (cartilage meeting around the intercondylar area would get it filled), which is why `subdivide_tibia` runs it per plate. `split_mesh_by_scalar` / `split_mesh_by_plane` cut triangles exactly along a linear-per-triangle level set in **numpy** (VTK's clip filters interpolate in float32, ~1e-8 area error), conserving area to double precision, keeping winding, copying cell data and interpolating point data; a level through a vertex reuses that vertex (no duplicate points / spurious open edges, which would otherwise read as FOV boundary to the hole rule). All shares are by `triangle_areas`, never voxel counts.
- The MRI femoral-head centre (`hip.py::get_femoral_head_center`, non-isotropic path) is a **seeded consensus sphere fit in true mm** (`_fit_femoral_head_consensus`): seed a sphere on the slab contour points medial of the top-slice centroid and within `C.FEMORAL_HEAD_SEED_DEPTH_MM` (30, about one head radius) of the top slab slice, then refit on every slab point within `C.FEMORAL_HEAD_CONSENSUS_TOLERANCE_MM` (2.5) of the current sphere until the inlier set is stable (cap `C.FEMORAL_HEAD_CONSENSUS_MAX_ITERATIONS`, WARNING logged if hit). The depth limit matters: the slab can run 40-70 mm below the head top (its bound still uses the pipelines' `x_ratio`), and a seed taken from those slices starts in the neck basin or calcar and stays there at every tolerance. The fit replaced a lateral cutoff at `0.9 * max_x` — 0.9 times an absolute voxel *index* — which made the centre depend on where the hip sat in the image and could not tell lateral head surface at the equator from neck surface below it. Pass the voxel spacing via the optional `spacing=` argument (all callers holding an `Image` do: proximal reference line, CCD, acetabular anteversion, CEA, subchondral, femoral offset). Array-only callers (alpha angle, acetabular depth, min distance) fall back to voxels of `(1, 1, x_ratio)` with a 1 mm in-plane voxel; that is still translation-invariant, but with the pipelines' current `x_ratio` its centre differs from the spacing fit by ~5 mm in z (median, max 14). No production caller is affected (the NaKo scripts are isotropic); task #10 (`x_ratio = spacing_z / spacing_x`) resolves it. The isotropic (NaKo) path is unchanged. Accuracy, checked against full-contour circle fits on the top head slices (pure head, independent of either fit): the old centre sat ~2.6 mm MEDIAL on image-left halves and on the reflected torsion path, and ~2.2 mm LATERAL on directly measured image-right halves (CCD, CEA, subchondral, femoral offset, acetabular anteversion), correlated with the image x position; the consensus centre's signed medial offset is ~0.0 mm (median -0.1 to -0.2) and its in-plane distance median 0.3 / p90 0.7 / max 2.0 mm. Pinned by `tests/unit/test_femoral_head_consensus.py` (head+neck phantom, exact translation, a calcar phantom for the seed depth) and `tests/characterization/test_head_centre_translation.py` (PA000001: centre/radius, Murphy with the knee fixed, anteversion, CCD). Still position-dependent, independently of the head fit (strict xfail there, task #9): Lee torsion, the knee condylar line and the alpha angle, all through slice rotations about the image centre. With the corrected centre, CCD and Lee agree better with the Augsburg readers but Murphy read further above them; part of that was Murphy's distal landmark (see the next bullet). Separately, the pipelines' `x_ratio = spacing_z / 2 * spacing_x` is not the slice aspect (`spacing_z / spacing_x`); the head's own sphericity supports the latter, but it has not been changed (the consensus fit uses `spacing`, not `x_ratio`). On this path `x_ratio` now only bounds the head slab walk, so it is inert on every dataset measured (Augsburg, NaKo and a straight-femur phantom give identical results at 1, 5.47 and 9.14); `calculate_anteversion` therefore derives it from the image (`spacing_z / spacing_x`) rather than hard-coding 1.
- Murphy's distal landmark (`femur.py::get_femoral_neck_base`) follows the published definition ("just above the lesser trochanter"): the femur centroid on the **first axial slice above the lesser trochanter's superior extent** — 10 mm up on the Augsburg hip MRI, 3 mm on whole-leg CT, 1 mm on isotropic NaKo, i.e. as close above the trochanter as the acquisition resolves. `_find_trochanter_minor` returns that extent alongside the point `get_trochanter_minor` reports, now `(x, y, layer)` (`y` used to be a copy of `x`). The centroid is a continuous index, paired with the unrounded head centre (`get_proximal_reference_line` keeps the int16 cast only for Lee and Tomczak, whose searches index the mask with it); the head-to-base axis is short (~25 mm in-plane on the hip MRI), so the former slice *through* the trochanter and the int16 truncation mattered — Murphy's positive bias against the Augsburg readers dropped by ~1-1.5°. A fixed 10 mm offset was tried and rejected on the NaKo raters' signed manual Murphy values (1 mm data, 120 hips): it reads +5.6° high with ICC2 0.85, where 0-5 mm levels give bias -1.2 to +2.2 and ICC2 up to 0.94. The Augsburg hips cannot distinguish offsets ≤ 10 mm (all pick the same slice), so that evidence comes from NaKo alone. A level less than `C.MURPHY_NECK_BASE_MIN_HEAD_DISTANCE_MM` (10) below the head centre — measured in mm from the image's own slice spacing — lies inside the head, i.e. the trochanter was mis-detected, and raises `RuntimeError` (4 Augsburg legs, 2 NMDID). The remaining Murphy bias is not explained by the distal landmark.
- Physical (mm) coordinates stay floats: `get_femoral_shaft_axis_ct` returns float endpoints in physical space (consumers: `calculate_ccd_ct`, `calculate_femoral_offset_projected(ct=True)`). Its MRI counterpart `get_femoral_shaft_axis` likewise returns unrounded (continuous-index) slice centroids (consumers: `calculate_ccd`, `calculate_femoral_offset{,_projected}`). Only *index* coordinates are rounded/cast, and only where an array is indexed. Casting mm coordinates to `int` truncates toward zero, which makes a measurement depend on the image's position in the scanner frame.
- Failures inside batch scripts and `compute_torsion.py` are caught per-measurement (`except (RuntimeError, AssertionError, ValueError)`) and written out as `np.nan` so a single bad patient does not abort a cohort run. Keep this behavior when extending those scripts.
