# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The repo has four loosely-coupled parts; the three Python parts share a single virtualenv and the `morphometry` package, and `frontend/` is a self-contained Node/Next.js app:

- `morphometry/` — the analysis library, layered as an acyclic dependency graph:
  - **`morphometry/measurements/`** — all public `calculate_*` measurement functions, one submodule per region (`hip.py`, `femur.py`, `knee.py`, `tibia.py`, `ankle.py`, `whole_leg.py`, `cartilage.py`). This is the public surface (re-exported from `morphometry.measurements`). Import measurements from here, e.g. `from morphometry.measurements.femur import calculate_femoral_torsion`.
  - **Region modules** at the package root (`hip.py`, `knee.py`, `ankle.py`, `femur.py`, `tibia.py`, `whole_leg.py`, `cartilage/`) hold the landmark / reference-line helpers (`get_*`) that the measurements build on. They must NOT import from `measurements/`.
  - **Leaf infrastructure**: `image_io.py` (the `Image` / `Segmentation` wrapper every function operates through), `geometry.py` (shared pure helpers: `fold_to_acute`/`fold_to_obtuse`, `split_left_right`, `slice_centroid_to_point`, `mirror_sagittal_coordinate`, `signed_axial_angle`, `validate_in_plane_isotropy`, `mirror_index_x`, `order_condylar_points`), `constants.py` (modality-scoped `SegmentationLabels` + tunable thresholds), `utils.py`, `bresenham.py`. These import no region/measurement code.
  - Dependency direction (enforced by `tests/test_import_graph.py`): `measurements/* → region get_* → geometry/utils/constants/image_io/bresenham`.
  - MRI vs CT: torsion / CCD / neck-center / bone-length have separate `_ct` functions (modality differs in landmark acquisition); the acetabulum / CEA / subchondral / offset family take a `ct=` flag. Shared `_core` helpers isolate the modality differences.
  - **Whole hip bone vs acetabulum**: `calculate_center_edge_angle` / `calculate_acetabular_anteversion` were written for masks that label the acetabulum separately (MRI/NaKo, isotropic). Whole-leg CT label maps have one label for the entire hip bone, so pass `acetabulum_radius_factor` (~1.4) to route them through `get_acetabular_surface` (in `hip.py`), which keeps only the bone *facing* the femoral head — per ray out of the head centre, the first bone voxel — so the iliac wing is shadowed rather than mistaken for the acetabular rim. That flag also switches CEA's angle into millimetres: the default index-space arithmetic is only valid for isotropic voxels, and on 0.8×0.8×3.0 mm CT it inflates a 25° angle to ~60°. Default `0` keeps the legacy behaviour, so the MRI goldens are untouched.
  - Torsion `calculate_*` return only the angle; landmarks come from `get_femoral_torsion_landmarks` / `get_tibial_torsion_landmarks`. Measurement functions never change their return arity based on `plot` — pass a matplotlib `Axes` / PyVista `Plotter` to `plot=` to draw overlays.
- `api/` — a FastAPI service (`api/main.py`) that ingests DICOM uploads or Orthanc callbacks, stores examination metadata in SQLite + images as `.nii.gz` files (`api/db`, `api/storage`), and dispatches model jobs to a **Redis/RQ worker** (`api/tasks`) that shells out to the docker images (see below). Layered: `routers` → `ingest`/`serializers`/`deps` → `db`/`storage`/`tasks` → `settings`/`runtime`. Config is env-driven via `api/settings.py` (`MORPH_API_*` / `.env`). `api/examination.py` is legacy, kept only for `scripts/migrate_pickles.py`. Torsion uploads are **two-phase**: `POST /upload/torsion/series` enumerates the DICOM series in a whole examination folder (grouping by SeriesInstanceUID, discarding junk, rendering previews) into a `pending_selection` examination; the user picks a series (whole-leg → auto-split, or three hip/knee/ankle series) via `POST /upload/torsion/select`, which materializes it and auto-starts the full pipeline. A whole-leg series is frequently a **gapped 3-station acquisition** (hip/knee/ankle slabs); `api/ingest/dicom.py::_detect_slabs` splits it at the position gaps and converts each slab on its own so SimpleITK doesn't average the gaps into a ~2×-inflated z-spacing (which would silently corrupt all superior-inferior distances) — see `api/README.md` "Multi-slab acquisitions". **Auth** (`api/auth/`): username/password login (`POST /auth/login` → signed Bearer token, argon2 hashes) coexisting with `X-API-Key` for machine clients; users are managed with `python -m api.users`. See `api/README.md`.
- `scripts/` — one-off batch processing scripts (`process_augsburg_*.py`, `process_nako*.py`, `combine_series.py`, etc.). Each script is self-contained and typically prepends `sys.path.append('/home/simon/Work/morphometry')` and hard-codes absolute data paths (e.g. `/home/simon/Data/...`); update paths when running elsewhere. `process_augsburg_reader_study.py` and `process_augsburg_large_dataset.py` write their xlsx with a `qc_flags` column appended after the measurement columns by `add_qc_flags` (the Murphy neck-base flags of that leg; Side is the *patient* side, so the image-left half lands on 'right'). A few are proper `argparse` CLIs — e.g. `compute_knee_cartilage_thickness.py -i <seg.nii.gz ...|dir> [--femur-label 3 --tibia-label 4 --tibia-bone-label 2 --femur-bone-label 1 --laterality-table lat.csv -o summary.csv --dump-json maps.json --visualize both --screenshot <dir> --html <dir>]` computes per-subregion knee cartilage thickness and optionally renders the 3D segment/heatmap views (via `plot_knee_segments`/`plot_knee_thickness`) as PNGs (`--screenshot`) and/or self-contained interactive HTML (`--html`). There is **no `--method`** any more (it is accepted and rejected with an explanation, so an old command line fails loudly). After the existing columns the CSV carries the paper's area-weighted statistics — `aMe_mm` (ThC.cAB.aMe, the number to quote), `tab_aMe_mm`, `aMax_mm`, `aMav_mm`, `aSD_mm`, `aMin_mm`, `aMiv_mm`, `tab_area_mm2`, `cab_area_mm2`, `denuded_fraction` — while `mean_mm`/`std_mm`/`min_mm`/`max_mm`/`n_points` stay the unweighted statistics of the per-position map (a "point" is now an in-plane grid cell of the knee's shared frame, not a voxel column). The JSON gains `statistics` and `frames` beside the per-bone maps. `-i` accepts multiple files and/or directories (searched recursively for `*.nii`/`*.nii.gz`); multiple inputs batch into one combined CSV (leading `subject` column) + one combined JSON (keyed by subject). All visualisation files land flat in the `--screenshot`/`--html` dirs named `<subject>_knee_<view>.<ext>`. Output paths ending without an extension are treated as directories (`summary.csv`/`thickness.json` written inside). The CSV's last column `qc_flags` (also a per-subject `qc_flags` key in the JSON) carries `cartilage.knee.scan_qc_flags`: `;`-separated `name:value` flags in `process_nmdid.py`'s format — `non_lpi_orientation:<codes>` (scan not LPI after reorientation), `tibia_transfer_far:<fraction>` and `femur_transfer_far:<fraction>` (that bone's `transfer_qc` far fraction above `TRANSFER_MAX_FAR_FRACTION`); empty = clean. Flagged scans are measured and written as usual; a scan for which both bones fail, or whose processing raises (with its orientation flag if it loaded), keeps one placeholder row (empty `bone`/`subregion`, NaN stats) so it and its flags stay visible. `process_nmdid.py -i <seg.nii.gz ...|dir> -o <dir> [--shard I/N --workers N --cohort-status cohort_status.csv --verdict usable review --limit N --overwrite --merge]` batches the whole-leg **CT** measurements (femoral torsion/Murphy, tibial torsion, CCD, femur & tibia length, femoral offset, mechanical axis deviation, HKA, center-edge angle, acetabular version) over the NMDID cohort, one CSV row per (case, image side). Built for SLURM: `--shard` (or `SLURM_ARRAY_TASK_ID` / `SLURM_ARRAY_TASK_COUNT`, see `process_nmdid.sbatch`) strides the cohort across job-array tasks that each fan out over their node's CPUs into their own `shard_XXX.csv`; `--merge` concatenates them. Rows are flushed per case, so an interrupted run resumes. Because these are whole-*body* scans, `clean_leg` drops the mislabelled arm bones (non-pelvis label components lying entirely above the hip bone) and the spine/rib fragments in the pelvis label; segmentations that are damaged in ways it will not silently repair are reported in a `qc_flags` column instead. That `qc_flags` column also carries the Murphy femoral-neck flags of `murphy_neck_base_qc` (`;`-joined onto the segmentation-integrity ones), so a row whose femoral torsion rests on a degenerate neck is marked while keeping its value.
 - `process_nako_large.py --chunk N [--input-root <dir> --output-dir <dir> --workers N --overwrite]` measures one chunk of the NaKo cohort (`<input-root>/chunk_N_segmentations`, `.nii.gz` only — the chunk dirs also hold three nnU-Net json files) into `results_chunk_N.csv`, in the original cohort-table layout (one row per Patient and *patient* Side; image-left half = patient right) with a `qc_flags` column appended last (that hip's Murphy neck-base flags, see the Murphy bullet below; empty = sound, and `AT_murphy` is written either way), plus `results_chunk_N.meta.json` (git commit, dirty flag, date, args). Each finished case is flushed to `results_chunk_N.partial.csv`, so a killed task resumes on resubmission (a case torn mid-write, or a partial with no complete row, is dropped and recomputed). A case that cannot be loaded is not flushed but retried once at the end of the run, then written as all-NaN rows; more than `--max-load-fail-frac` (0.01) load failures in a chunk fail the run without finalising (a broken mount, not bad files). A worker that dies hard raises `BrokenProcessPool` rather than hanging and saves the cases in flight to `results_chunk_N.suspects.json`; the next run measures each suspect alone first and writes one that still kills its worker as all-NaN rows. Both kinds of NaN case are listed in the meta file (`load_failed`, `crashed`). When every case is in, the rows are sorted into `results_chunk_N.csv` and the partial file removed. A finished chunk CSV is refused without `--overwrite` (which starts the chunk afresh). `--output-dir <dir> --merge [--expected-chunks 20]` concatenates the chunks in numeric order into `<dir>/results.csv`, refusing missing, unfinished or out-of-range chunks and duplicate (Patient, Side) rows. `process_nako_large.sbatch` is the SLURM array (tasks 0-19, one chunk each, 32 CPUs) writing to a fresh `~/Data/nako/rerun_<short sha>`; it refuses a dirty checkout, and the checkout must not change until the array has finished. Acetabular anteversion now runs with `isotropic=True` like every other NaKo measurement (before: `isotropic=False`, the consensus head-centre fit). Cohort tables from before this change also hold empty rows named after the json files (`dataset`, `plans`, `predict_from_raw_data_args`); the cohort is 30,407 cases.
 - `analyse_thinnest_point_flexion.py -i <dir> [--tibia-bone-label 2 --femur-bone-label 1 -o <dir> --screenshot/--html <dir> --visualize]` groups `K<subject>_<angle>_<load>.nii.gz` segmentations by `(subject, load)` and tests whether the thinnest point migrates posteriorly with flexion — measured as the thinnest point's arc-length fraction along the femoral subchondral bone area in the sagittal cross-section of the **femoral frame** through it (`femur_regions.articular_arc_fraction`; 0 = anterior/trochlea, 1 = posterior condyle, clamped to the outermost cross-section for a point up to `max_outside_mm` (1 mm) past the condyle's medial-lateral edge — without any clamp 16 of 288 cohort rows were NaN, because a cut plane through the very edge of the mesh intersects nothing; further out than that the cross-section is a near-degenerate sliver whose fraction is not comparable, so it stays NaN), which is built from the femur alone and so does not move with the knee's pose. It is only *approximately* flexion-invariant, though: the arc is normalised over a contour whose anterior end is the edge of the labelled trochlear cartilage, which step 3 already records as not flexion-reproducible. Measured on fixed anatomical landmarks (each femoral region's area-weighted tAB centroid), the arc fraction wobbles across the four flexion scans of one knee with a within-series SD of 0.017-0.065 per region (max 0.19) — 15-20% of the effect size the analysis looks for (median slope 0.0039/deg × 90° ≈ 0.35) — summarised per series (Spearman ρ + slope) and cohort-wide (binomial sign test). `detail.csv`'s point columns are `thin_u`/`thin_v`, the thinnest point's cell in the knee's shared in-plane frame (they were image indices `thin_x`/`thin_y` before), and there is no `--method` (see the thickness script). **Every earlier run of this script is superseded**: the thickness definition, the map keys, the `ap_fraction` coordinate, the joint-facing-sheet selection and the thinnest-point refinement fix all changed. The per-compartment sign tests in particular are **not robust to the search restrictions**: the always-on full-window rule removes a median 27.3% of the candidate cells and moves the chosen cell in 279 of 279 compartment results (median |Δ arc| 0.233, max 1.0), and switching it off reorders which compartment looks most significant (whole knee 20/24, patient-left 21/24, patient-right 18/24 without it, against 20/24, 22/24 and 21/24 with it). Quote the per-compartment p-values only with that caveat, or not at all. At the *same* point the old (image-space) and new (femoral-frame) `ap_fraction` formulas differ by a median 0.079 over the 89 clean scans where both are defined (p90 0.670, max 0.990; per angle, median |Δ| 0.071 / 0.055 / 0.080 / 0.187 at 0/30/60/90°), and their Spearman correlation is only 0.54 — they are not interchangeable. Everything is done per **compartment** — `both` (whole knee), `left`, `right`: `detail.csv` is long format (exactly one row per parsed scan × compartment, `compartment` column after `angle`), series and `summary.csv` (insufficient series kept with NaN stats) are keyed by `(subject, load, compartment)`, and the sign test is reported separately per compartment (separate, uncorrected tests; the two loads of one subject are not independent). 'left'/'right' is the PATIENT side (from the NIfTI header after LPI reorientation), not medial/lateral: patient-left is medial in a right knee and lateral in a left knee, so a per-side sign test reads as medial or lateral only if every knee in the cohort is the same side. A compartment whose search fails becomes NaN for that scan (stderr warning) without dropping the other compartments; a scan whose thickness pipeline fails is written as NaN for all three. `detail.csv`'s last column `qc_flags` holds the scan's `scan_qc_flags` (same flags as the thickness script; a scan that loads but then fails keeps its orientation flag), and `summary.csv`'s last column `qc_flagged_angles` lists the `;`-joined angles of the series' flagged scans; flagged scans still enter the statistics. Visualisations draw one arrow per compartment in a single scene.
 - `report_knee_cartilage_cohort.py -i <seg.nii.gz ...|dir> -o <dir> [--workers N --include-flagged --exclude SCAN ... --min-angles 3]` regenerates the `dfg_knees` cohort tables this file and `docs/wirth_eckstein_2008_plan.md` quote — the Table I analogue (tibial region shares per plate), the Table II analogue (femoral thirds per condyle), tAB/cAB areas and the denuded fraction per subregion, the thickness statistics per subregion, the whole-bone `aMe` per flexion angle, the loaded-vs-unloaded and across-flexion spreads, and a QC summary. Writes `scan_metrics.csv` (long: scan × bone × region, plus the `plate_*` / `cf_*` / `whole` aggregates), `scan_geometry.csv` (long: scan × geometry/QC scalar), `cohort_summary.csv` (long: one row per statistic, `table, scope, region, unit, n, mean, sd, min, max, p50, p90, paper`; carries no timings, so two runs that computed the same numbers give the same file whatever `--workers` was), a human-readable `report.md` and `report.meta.json` (commit, dirty flag, branch, host, date, args, inputs, scan counts, per-bone timings — the provenance a "re-derivable" table needs). An aggregate row's `aMe`/`cMe`/`bMe`/`tab_aMe` are **exact** (each direction weighted by its own area — cAB for `cMe`, AC for `bMe`) and so are `aMin`/`aMax`/`tab_aMin` (min/max over the parts, so one denuded triangle makes `tab_aMin` exactly 0); its `aSD`/`aMav`/`aMiv`/`tab_aSD` are area-weighted means of the subregion values and under-state the union's spread — `report.md` says so above the table. Failures are per scan and per bone, and every scan keeps its `scan_qc_flags` string in a `qc_flags` column; by default the statistics cover the scans that measured **and** carry no QC flag (93 of the 96 `dfg_knees`), while `--include-flagged` / `--exclude` reproduce an older set (the 94-scan tibial table: `--include-flagged --exclude K7_90_belastet K11_90_belastet`). The reproducibility sections are **spread, not precision** — the loaded/unloaded and flexion scans are different acquisitions of a repositioned knee, not repeats, so they are not comparable with the paper's 19-84 µm test-retest rms SD — and the pooled rows cover the 20 subregions only, never the aggregates. Region keys are patient-side and the knees' laterality is unrecorded, so the paper's medial/lateral values are printed in their own table and their own summary rows, never paired with ours.
 - Two **analysis** scripts answer a specific backlog question rather than producing a cohort table, and each has a findings doc that is the thing to read; both measure the 50-patient Augsburg reader study and write only inside their `-o` directory. `analyse_reader_bias.py -o <dir> [--workers 12]` decomposes the CCD / Lee / Murphy disagreement with the two readers into an inter-reader scale, a shared-landmark component and a method-specific one (task #7 → `docs/augsburg_reader_bias.md`, **which carries a 2026-11-04 partial retraction**: task #2 showed the Lee−Murphy separation is anatomy, so the decomposition's "shared ≈ 0 / method-specific ±4.6°" split and its "the pipeline's gap is ~13° too wide" both invert — the readers' columns are what fail to reconcile, and no bias computed against them should be read as a pipeline defect until that is settled). `analyse_ccd_x_ratio.py -o <dir> [-i <root> --tables <dir> --workers 12 --skip-torsion]` sweeps the `x_ratio` slice-thickness factor over the MRI CCD, reporting the cohort mean, the reader-free within-patient left/right agreement, the bias against the readers and the size and slice span of the neck point cloud each factor selects, plus a torsion-invariance check at the two named factors (task #6 → `docs/ccd_x_ratio.md`). **Neither script picks a parameter**, and `analyse_ccd_x_ratio.py` says so in its own docstring: its criteria disagree and are computed on the same patients any choice would then be quoted against. Two more answer a question about the **whole-leg CT** cohort over sshfs and take `-i <dir|file ...> -o <dir>`: `survey_ct_spacing.py` reads **headers only** (so it covers the cohort in minutes) and reports each file's post-LPI in-plane spacing, whether the task #10 isotropy assert would refuse it and whether the reorientation achieves LPI — permuting the header zooms into the post-LPI axis order is the whole point, since the reorientation can move the slice axis *into* the plane, which is how `dfg_knees` comes to violate the precondition; `survey_ct_murphy_qc.py` loads each case properly (re-using `process_nmdid.py`'s own `load_case` / `split_legs`, so the legs are prepared exactly as production rows are) and reports the Murphy landmark failure reasons, the flag rate and the **axis-length distribution against the threshold**, because a rate alone cannot say whether a cohort straddles the gate or sits far from it (task #3 → `docs/ct_murphy_qc.md`, task #10 → the spacing survey quoted in Core data flow item 3).

## Core data flow

1. **Images** — every analysis function expects a `morphometry.image_io.Image` or `Segmentation`, which wraps either a `nibabel.Nifti1Image` or a `SimpleITK.Image`. Construct with `Image.from_nibabel(...)` / `Segmentation.from_nibabel(...)` or `Image('nibabel').read_image(path)`.
2. **Coordinate system** — masks must be placed in **LPI** orientation before measurement. Always call `seg.transform_coordinate_system()` right after loading; `remove_outliers()` is also commonly applied before measurement. The reorientation only permutes/flips voxel axes, so a strongly oblique scan can come out labelled non-LPI: `Image.achieved_axcodes` (live `nib.aff2axcodes` of the current affine) and `Image.orientation_ok` (achieved == requested `axcodes`; `None` before any request) record it, with one WARNING on the `morphometry` logger; the behaviour itself is unchanged. Known cases: 3 of the 96 `dfg_knees` scans — K7_90_belastet (raw IAR -> LSP), K8_90_belastet and K11_90_belastet (raw SPR -> LIA). The scanner-frame tilt of the slice axes is *not* the cause: it comes from knee flexion and is harmless (axis 2 vs world S-I median 4.6/11.1/24.1/38.7° at 0/30/60/90° flexion; 9 healthy scans exceed 40°, K10_90_belastet 57.5°, all LPI and fine). What is wrong is the anatomy's rotation in the index frame: the tibial plate normal is ≤17.0° from index axis 2 in all 93 LPI scans but 25.7° (K11), 75.5° (K7), 83.0° (K8) off, and the femur-minus-tibia cartilage centroid along axis 2 is -28 to -12.2 mm in the 93 vs -2.6 (K7), +1.6 (K8), +35.3 mm (K11). It surfaces as a near tie in axis labelling (K7's first axis: 0.706 S-I vs 0.703 A-P) that nibabel's greedy, voxel-axis-ordered `io_orientation` breaks differently after the permutation. The user attributes these scans to a scanner misconfiguration; they are flagged in the knee scripts' `qc_flags`, not fixed or dropped. K11_90_belastet is additionally a separate defect the orientation flag catches only by coincidence: 1 mm isotropic, 344 slices, 512 mm FOV (all others 0.31×0.31×0.75 mm, 172 slices), tibial cartilage of 9.4k voxels scattered over a 258×318×213 mm box; its tibia subdivision fails ('plates overlap'). `orientation_ok` is only meaningful on the reoriented image (and crops/splits/reflections of it): `mirror_image_left_right` copies `axcodes` but flips the affine, so a mirrored LPI image reads `False` (RPI).
3. **Left/right splitting** — pipelines split a full-body mask at `array.shape[0] // 2` into `left_*` / `right_*` halves. Note: "left" / "right" refers to the *image* side, not the patient side. Functions take a `side='left'|'right'` argument and document this convention explicitly. Whenever a half is used as an `Image`/`Segmentation` (i.e. with geometry), split with `image_io.split_image_left_right` — never wrap `array[half:]` in the parent's affine. Its guarantee (both backends): the left half keeps the parent geometry; the right half's index `i` maps to the same physical point as the parent's `i + [half, 0, 0]`. The parent affine on the right half put every right-side physical coordinate `half * spacing_x` off (195 mm on the CT fixture). Index-space landmarks from a right half still need `+ half` on x to address the whole mask (e.g. `right_fhc_adj[0] += left_mask.shape[0]`). It shares its affine-advance with `split_ct_image`'s z-crops and the public `image_io.crop_image(source, axis, start, end)` (all via `_crop_axis`); the API's changepoint hip/knee/ankle split (`api/ingest/dicom.py::_split_volume`) uses `crop_image` too. Two left-right flips exist and are not interchangeable for physical-space code: `image_io.mirror_image_left_right` relabels indices (mirrored index `i` ↦ parent `n-1-i`, every voxel keeps its physical location — a left leg stays a left leg physically), while `image_io.reflect_image_left_right` reverses the voxels but keeps the geometry, producing the physical *mirror twin* (a left femur becomes a right femur in index and physical space). `geometry.split_left_right` is the geometry-free array split.
   **Femoral torsion is mirror-equivariant by construction.** The proximal-femur and knee landmark searches are written for a left image half; a right half is measured as the reflection of a left one: `get_proximal_reference_line{,_ct}(side='right')` and `measurements/femur.py::_mri_torsion` / `_ct_torsion` reflect the right half (`reflect_image_left_right`, knee arrays `[::-1]`), run the left-side code, compose the angle there with the left conventions, and map landmarks back with `x -> n-1-x` (`geometry.mirror_index_x`, with `geometry.order_condylar_points` restoring the reported endpoint order). A mirrored left half through `side='right'` therefore gives exactly the left result (pinned by `tests/characterization/test_femoral_torsion_equivariance.py`, MRI Lee/Murphy + CT, stage by stage; pure composition in `tests/unit/test_torsion_angle_equivariance.py`). This replaced separate right-side branches that were systematically different: a flip off by one voxel (`c + (n//2-c)*2` instead of `n-1-c`), a head trim that scaled an index and so was not the mirror of the left trim, `astype(int16)` truncation of the head centre (floor is not mirror-consistent) and an asymmetric knee condylar search. `calculate_anteversion` shares the reference line, so its right side is equivariant too.
   **The CCD and the tibial torsion are too, the same way.** `measurements/hip.py::calculate_ccd` measures a right image half as the *mirror* of a left one (`mirror_image_left_right` of the hip and knee images, left-side code) and `calculate_ccd_ct` as the *reflection* (`reflect_image_left_right`); the two are not interchangeable here. The MRI CCD composes its angle from physical coordinates spanning two images whose affines have different origins, so it needs an operation that keeps every voxel's physical position — a reflection mirrors each image about its own array centre, and those are the same world plane only if the two images share an index-to-world x map (origin *and* direction), which separately acquired hip and knee series do not: equal array widths are not sufficient, and on Augsburg, where both halves are 192 wide, reflecting each about its own centre still costs a median 1.22° (5.7° on PA000031, whose hip and knee origins are 13.5 mm apart) — whereas the CT landmark code reads physical directions (which physical x is lateral) and so needs the mirror-twin leg. `measurements/tibia.py::_tibial_torsion_points` reflects the knee and ankle arrays (`[::-1]`), composes with the left conventions and maps the landmarks back, so `get_tibial_torsion_landmarks` now does depend on `side`. Pinned by `tests/characterization/test_ccd_tibial_equivariance.py` (both probes, MRI + CT); its MRI CCD probe has to reflect the hip and knee images about one *common* world plane rather than each about its own centre, which is a property of the probe, not of the measurement. Measured over 50 Augsburg cases, 60 NaKo hips and the 46 NMDID verification legs, the two sides previously disagreed by a median 0.16–0.23° (MRI CCD, max 0.70), 0.21–0.32° (NaKo isotropic hip-only CCD, max 1.00), 0.85–1.02° (CT CCD, max 3.14), 0.8–1.1° (Augsburg tibial torsion) and 1.7° (CT tibial torsion), and now agree exactly; every left-side value is bit-identical.    **The knee rotation angle composition is rotation-invariant and signed too, and its direction is the published one.** `measurements/knee.py::_knee_rotation_angle` returns `geometry.signed_axial_angle` from the (undirected) posterior **femoral** condylar line to the (undirected) posterior **tibial** condylar line, folded into (-90, 90]; `side='right'` negates the x components, so a knee and its mirror twin read the same. Of it, Anzillotti et al. (J Exp Orthop 2026;13(2):e70708, following the standard technique of Diederichs et al., Am J Sports Med 2013;41:51–57) write "this measurement is positive if the tibia is externally rotated compared to the femur" — which is exactly the shipped `+1` in `measurements/knee.py::KNEE_ROTATION_POSITIVE_SIGN`.    **The axial-plane angles are composed in index space, which assumes equal in-plane voxel spacing (task #10).** `geometry.signed_axial_angle` — and with it `_femoral_torsion_angle`, `_tibial_torsion_angle` and `_knee_rotation_angle` — works on voxel *indices*, as does `measurements/femur.py::_proximal_angle`, the neck angle against the image x-axis that `calculate_anteversion` reports. At spacing `(sx, sy)` a physical direction `(cos t, sin t)` has index direction `(cos t / sx, sin t / sy)`, i.e. index angle `atan2(k sin t, cos t)` with `k = sx / sy`, so on in-plane anisotropic data the angle *between* two lines comes out sheared by an amount that depends on how the limb happens to lie in the slice, not only on `k` — and a *single*-line angle like the anteversion's takes that shear directly, with none of the partial cancellation a two-line angle gets. Worst case over all limb orientations, a true 15 / 30 / 45° angle is off by at most 0.01 / 0.03 / 0.04° at `k = 1.001`, 0.15 / 0.29 / 0.40° at 1.01, 1.5 / 2.8 / 4.0° at 1.1, 7.3 / 13.8 / 18.7° at 1.5 and 20.1 / 35.5 / 44.7° at 2.4; the error grows with the true angle, so the sup at `k = 1.001` is 0.0573° (approached as the true angle tends to 90°, where the folded angle can also cross the (−90, 90] seam), not the 0.04° of the 45° column. At `k` = 2.4 a true 15° reads anywhere in [6.3°, 35.1°]. **Measured spacing survey** (header zooms permuted into the post-LPI axis order — the reorientation can move the slice axis *into* the plane): Augsburg MRI **5715/5715** `.nii.gz` under `preprocessed/` square in plane (values 1.09375, 1.145833, 1.25, 1.302083, 1.640625 mm; slice 4–10 mm — but note that list is the **union over regions, and the per-region sets differ**, which is what makes a spacing-dependent hazard region-specific: the 952 **knee** segmentations carry `{1.09375: 949, 1.145833: 1, 1.302083: 1, 1.640625: 1}` and the 951 **hip** ones `{1.09375: 949, 1.145833: 1, 1.25: 1}`, so 1.25 mm occurs on no knee mask and the coarsest knee spacing, 1.640625, occurs on no hip mask — which is exactly why the millimetre-ordering defect recorded under the Murphy gate is *demonstrated* on the condylar line and only *possible* on the Murphy axis) and 450/450 in `reader_study_augsburg/` at 1.09375, NaKo sample 1.0 mm isotropic 60/60 — every one of them with its two in-plane zooms **bit-identical**, so nothing legitimate sits near the tolerance. ## Conventions worth preserving

- Docstrings are verbose: one-line purpose, `:param:` / `:return:` for each parameter. New public functions should follow this style (see e.g. `morphometry/measurements/hip.py::calculate_ccd`).
- Measurement functions commonly accept a `plot: bool | plt.Axes` argument — passing an `Axes` draws overlays instead of creating a new figure. Preserve this pattern when adding new measurements.
- The ray-traced subchondral femoral-head-to-acetabulum distance (`measurements/hip.py::calculate_subchondral_distance_ray_tracing{,_ct}`) aims its ray cone with `cone_axis`, which defaults to **`'superior'`** (world `+z`, via `_superior_direction`). That axis samples the weight-bearing acetabular dome in every subject, independently of the labelling scheme. The former default `'acetabulum'` (FHC → peri-acetabular centroid) is retained as opt-in legacy behaviour only: the centroid is dragged ~46° medially by the ischium/pubis in the label, so roughly half its rays cross the non-articular **acetabular fossa** — where the head contacts no bone — inflating the mean by ~1.5 mm and roughly tripling its spread (the two modes agree, 3.65–3.77 vs 3.78–3.94 mm, over the innermost 0–20° where both sample true lunate surface). Because the fixed axis no longer aims at the label, 3.5–18.5% of rays clear the lateral acetabular rim and are dropped; heavy loss is logged as a WARNING on the `morphometry` logger, thresholded by `min_ray_fraction` (0.7). `docs/illustrations/plot_subchondral_3d.py --axis` reads its default off this signature so the illustration cannot drift from the library.
- Both `extract_subregions` enforce subregion contiguity (`_remove_subregion_fragments`, keep 26-connectivity components ≥ 20% of the largest): a subregion is one anatomical patch, but the nearest-tAB-triangle transfer can hand a voxel a region its own patch does not touch (across the intercondylar notch, say). Both bones now subdivide on the bone surface, so this is only a safety net; it is a no-op on clean scans (single-component subregions), and it affects only the voxel point clouds (`plot_segments`), never the thickness, which is measured on the surfaces.
- **Tibial subregions follow Wirth & Eckstein 2008** (`morphometry/cartilage/tibia_regions.py::subdivide_tibia`, plan step 2; replaced the voxel-sphere/bounding-box scheme outright, no legacy switch). They are defined on the tibial subchondral bone area (tAB, `surface.py`) in world mm, so `Tibia` now needs the **tibial bone label** (`bone_label=2`; `tibia_bone_label=2` on `calculate_tibial_cartilage_thickness` / `calculate_knee_cartilage_thickness` / `calculate_thinnest_cartilage_area`; `--tibia-bone-label` on `compute_knee_cartilage_thickness.py` and `analyse_thinnest_point_flexion.py`); a missing bone label raises. Plates = the two largest edge-connected cAB components (`find_plates`; second ≥ `min_plate_ratio` 0.2 × largest, else a fallback area-weighted 2-means split of the largest — never fired on the 96 `dfg_knees`), named by **patient side from RAS world x** (smaller x = patient left; this rests on the header, as before). Other covered islands are dropped unless enclosed by a plate (median 0.15 mm², max 0.66 mm² per knee over the 94 usable knees; 15 mm² on the broken K7_90_belastet). tAB is hole-filled **per plate** (`total_subchondral_area` with only that plate's cAB covered), so the intercondylar area can never be filled even if the cartilage plates touch. Per plate: centre of gravity S and principal axes b1..b3 from the **exact area-weighted triangle second moments** (`area_moments`; the paper uses vertices), b3 = normal oriented superior, right-handed. Central (`c`) = elliptical cylinder along b3, `rho = sqrt((x/σ1)² + (y/σ2)²)` with σ1, σ2 the in-plane standard deviations (our reading of the paper's unspecified λ1/λ2: a uniform elliptical plate gives a scaled copy of its outline), level found by bisection on the exactly cut mesh to 20% (`central_fraction`) of the plate tAB ± 1e-5. Peripheral = two planes through S containing b3 at ±45° to `tc` (S→other S, projected into the plate plane): internal (`i`) faces the other plate, external (`e`) opposite, anterior/posterior (`a`/`p`) by world +y (no fibula landmark, the paper's reference). Cartilage voxels take the region of the nearest tAB triangle centroid (`TibiaSubdivision.region_codes_at`, world mm), stored per point in `Tibia.point_labels`. Transfer QC: `Tibia.transfer_qc` (`tibia_regions.transfer_qc`: median/p99/max voxel-to-tAB distance, `far_fraction` beyond `TRANSFER_FAR_MM` 6 mm) and a WARNING on the `morphometry` logger when `far_fraction` > `TRANSFER_MAX_FAR_FRACTION` (1%) — clean `dfg_knees` max 4.8 mm, K7_90_belastet 49% beyond 6 mm (max 45 mm), the only knee flagged; `classify_point` is a single lookup. `Tibia.plot_regions()` draws the labelled tAB. On the 96 `dfg_knees` (1 failure, K11_90_belastet, broken segmentation: 1 mm voxels, tibia label fills the volume; K7_90_belastet runs but its tibial cartilage is ~¼ of the unloaded scan's) the region shares of the plate tAB are, patient-left / patient-right plate (n=94): c 20.0/20.0, e 16.9/15.9, i 15.6/14.1, a 23.8/25.0, p 23.8/25.0 % (paper MT/LT: c 20/20, e 16.0/17.7, i 15.6/17.5, a 24.2/22.6, p 24.1/22.2); belastet vs unbelastet same subject/angle: median |Δshare| 0.14 pp (max 1.3); across flexion angles within one subject/load: median SD 0.21 pp. All of these re-derive from `scripts/report_knee_cartilage_cohort.py` to the decimal shown (on its default 93-scan clean set as well as on this 94-scan one). Subdivision alone ~1-2 s per bone, a whole knee including both bones' thickness ~15 s single-process on a 32-core workstation (the ~3 s / ~20 s recorded earlier were a different machine; timings are not a regression signal). **Naming / laterality**: keys stay patient-side (`clt … plt` = patient-LEFT plate, `crt … prt` = patient-RIGHT; display `cLT`/`cRT`) whatever the laterality, so `find_thinnest_area`, `split_tibia_thickness_by_compartment`, plotting and the scripts are unchanged. `Tibia(laterality='left'|'right')` / `anatomical_tibia_names` / `rename_tibia_regions` give the paper's medial/lateral names (right knee: patient-left plate = MT; left knee: patient-right plate = MT) — there the `LT` means *lateral*, so `split_tibia_thickness_by_compartment` refuses any dict holding `*MT` keys. `compute_knee_cartilage_thickness.py --laterality-table CSV(subject,laterality)` adds an `anatomical_subregion` CSV column. **Do not pool tibial subregion rows produced before and after this change**: K1_0_unbelastet knn `clt` 1.885 -> 1.800 mm, `crt` 1.414 -> 1.311, `elt` 1.208 -> 1.370, `plt` 1.984 -> 1.729, `irt` voxels 916 -> 590. (The femoral rows moved then too, because their A-P window was cLT/cRT's extent; they have since been redefined outright, see the femoral bullet.) The voxel-sphere central region of 60425aa (and `calculate_ellipse`, `get_plate_corners`, the KMeans/BFS plate split, `tests/unit/test_tibia_central_region.py`) is gone; pinned now by `tests/unit/test_tibia_regions.py` (20% ± 1e-4, circular plate → four 20% wedges, invariance under 20° axial rotation / 7° slope / anisotropic + oblique sampling / SimpleITK, mirror swaps plates, enclosed intercondylar area not filled, denuded hole filled).
- `Tibia`/`Femur` clean their extracted cartilage mask before any processing (`_remove_mask_outliers`, `outlier_ratio=0.1` ctor arg): per-label 26-connectivity components smaller than the ratio of the total cartilage volume are dropped, removing mislabelled blobs / detached clusters. Legit cartilage (femoral horseshoe, the two tibial plateaus) is far larger than the threshold and retained; pass `outlier_ratio=0` to disable. **It now affects only the voxel point cloud** (`point_labels`, `extract_subregions`, `plot_segments`, the transfer QC): the subdivisions and the thickness read the label array directly, through `cartilage_coverage` / `articular_surface_mesh`. A stray blob is dropped from those by other means — the surfaces keep only the largest connected component of the bone (or of the bone+cartilage union), so a detached blob is not meshed at all, and a blob next to the bone can at most mark a few bone triangles covered.
- `find_thinnest_area` (re-exported; wrapper `calculate_thinnest_cartilage_area`) locates the thinnest *area* of the tibiofemoral cartilage robustly: it sums the tibial+femoral thickness maps over the in-plane cells present in *both* (the contact region), rasterises to a dense grid, NaN-aware median-smooths (kernel `k` derived from `neighbourhood_mm` / the frame's `grid_mm`, forced odd) to reject single-cell outliers, argmins for the neighbourhood centre, then refines to the actual thinnest cell within a radius disc. Positions are `(u, v)` cells of the knee's shared in-plane frame, **not voxel indices** (see the thickness bullet); both maps must be keyed in the same frame or it raises (`_overlap_spacing`), which is what stops a femur measured without a tibia from being paired up with a tibial map. **Read the warning on the function before using its output.** A cartilage map stops rather than fades, and `cartilage_coverage`'s distance test puts a band of near-zero cells at every cartilage edge, so the global argmin of a knee is almost always a rim cell. Two restrictions keep the search off it, both bearing on the same artefact: the neighbourhood-centre search is restricted to cells whose whole `k x k` window lies inside the overlap footprint (we are looking for the thinnest *area*, so the area has to be fully measured), **and the refinement disc now obeys the same restriction** — it did not, which is why the shipped step-4 code returned a rim cell on most knees: over the 93 clean `dfg_knees` the femoral thickness at the returned point had a median of 0.62 mm and was below 1 mm in 67% of results (tibial 0.71 mm, 79%) against real cartilage of 1.3-3.5 mm; with the refinement restricted those become 1.51 mm and 11%. **A residual remains at the extremes of flexion**: at 0° and 90° the contact genuinely runs off the end of the labelled condyle, so 18% and 41% of results still read a femoral thickness below 1 mm and the arc position of the point piles up against the trochlear or the posterior end — how much of that is the label edge and how much real contact geometry cannot be told from these segmentations. For that residual `edge_margin_mm` (distance from **each bone's own** map boundary) and `min_thickness_mm` exist, both **off by default**: every artefact indicator improves monotonically with the margin (0/2/3 mm → 14.0/11.1/5.7% of results below 1 mm femorally) because eroding the search region just drives the answer to the middle of the contact, so the data cannot choose a value, and for a flexion trend any value biases towards the null. Anything ≤ 1.5 mm is a no-op at the default neighbourhood and grid. If nothing survives, the whole overlap is searched and a WARNING is logged. Returns `{point, center, center_thickness, combined_thickness, tibial_thickness, femoral_thickness, kernel_size}` (`center_thickness` is the robust smoothed value, `combined_thickness` the raw value at `point`). `plot_thinnest_point` (re-exported; also `calculate_thinnest_cartilage_area(..., plot=pv.Plotter)`) renders the cartilage in 3D (`base='thickness'` heatmap or `base='segments'` voxels) and points a red arrow at the thinnest point — its 3D position is the midpoint of the two bones' articular surfaces recorded for that cell (`ThicknessMaps.positions`, `thinnest_point_position` — the former private `_thinnest_point_physical`, which now takes the two thickness maps rather than the `Tibia`/`Femur`). Given a `{label: result}` dict instead of a single result, it draws one labelled arrow per entry (`left` red, `right` blue, `both` black; `None` entries skipped).

- **Femoral subregions follow Wirth & Eckstein 2008** (`morphometry/cartilage/femur_regions.py::subdivide_femur`, plan step 3; replaced the tibia-relative CWBZ scheme outright, no legacy switch). Like the tibia they live on the femoral tAB (`surface.py`) in world mm, so `Femur` now needs the **femoral bone label** (`bone_label=1`; `femur_bone_label=1` on `calculate_femoral_cartilage_thickness` / `calculate_knee_cartilage_thickness` / `calculate_thinnest_cartilage_area`; `--femur-bone-label` on both knee scripts); a missing bone or uncovered bone raises. **Femoral frame** (bone only, so it does not move with flexion): shaft axis = the first principal direction of the centroids of 3 mm cross-sections of the femur in a band 5 mm below to 25 mm above the top of the articular surface (`estimate_shaft_axis`), seeded by bone-centroid minus cartilage-centroid, 3 refit passes, proximal bins dropped while they hold < 0.75 of the next bin's voxels (an incomplete, FOV-cut cross-section has a biased centroid). That band is *metaphyseal on purpose* (it even starts 5 mm inside the condylar flare, not in the shaft): a knee FOV holds only 25-40 mm of femur above the cartilage and its proximal end is cut, often very obliquely, differently in different acquisitions of the same knee. **The band was chosen by flexion reproducibility on these same 96 scans, so the invariance figures below are not an unbiased estimate of it, and it is not the argmax of its own objective.** Over the 24 series (cF-area CV averaged over the two condyles, median/p90/max; A-P-extent CV median/max): (-5,25) 2.41/4.40/6.66 and 1.47/2.86; (-5,35) 2.54/3.45/4.48 and 0.14/2.22; (0,30) 2.77/3.80/4.16 and 1.63/3.75; (5,35) 2.53/3.90/5.25 and 1.61/8.57 plus one scan it cannot fit at all. (-5,35) is therefore at least as defensible as the default, which only wins the cF-CV median. What the band moves and does not: the thirds' *shares* barely (max difference between any two of those four bands, per scan: median 0.24 pp, max 1.58), the shaft axis by a median 1.9° (max 7.5°, (-5,25) vs (-5,35)) and the cF area and A-P extent measurably (median 0.3%, max 4.2%) — i.e. exactly the quantities the reproducibility figures are about. `subdivide_femur(shaft_band_mm=..., shaft_bin_mm=..., shaft_min_bin_ratio=...)` exposes it. M-L axis = the posterior condylar line (`posterior_condylar_axis`, iterated 3x from world +x, orthogonalised against the shaft axis, oriented patient-right); A-P = `cross(prox, ml)` — **no world direction is consulted for anterior**, it follows from the right-handed frame, which is why a 90°-flexed knee needs no special case. Because the M-L axis *is* the posterior condylar line, both condyles' posterior ends share one A-P coordinate. **Landmarks**: the trochlear notch is read off the *bone*, not the cartilage (`notch_depth_profile` / `find_trochlear_notch`): per 1 mm coronal slice the most distal bone coordinate in each 1 mm M-L bin, the valley depth = the drop from the lower flanking maximum to a bin between them (an empty bin = the open fossa counts as infinitely deep), then walk anteriorly from the deepest slice until the valley is shallower than `notch_depth_mm` (8; the fossa is 20-30 mm deep, the trochlear groove 3-6, and the profile falls ~1.5 mm per mm there, so ±2 mm of threshold move the border ~1 mm). How far the trochlear cartilage is labelled across the groove varies between acquisitions of one knee and the bone does not, which is why the cartilage-gap version of this was dropped. cF = notch plane (normal = A-P axis, i.e. parallel to the shaft) back to `weightbearing_fraction` (0.6; 0.75 is the other published choice) of the way to the condyle's posterior tAB end. **Thirds**: normalised arc length across the condyle (`arc_length_coordinate`): cut cF's tAB into coronal cross-sections 0.5 mm apart, parametrise each contour by arc length from its internal (notch-side) end, interpolate onto the vertices, `split_mesh_by_scalar` at 1/3 and 2/3 — the paper's per-triangle-strip construction as a continuous field, so the triangulation need not be strip-ordered. The articular surface wraps proximally round the posterior condyle, so a coronal plane in the back of the window cuts it twice; within the window the two sheets are separate patches, cF is the largest and the rest goes to the posterior zone. Re-measured with `_largest_patch` disabled and everything else fixed: without it 9 of the 93 clean scans have a third more than 1.2 pp off 33.3%, the worst being 40.5% (K7_90_unbelastet). The discarded patch is a sliver of the window in a healthy subdivision (per condyle: median 0.00%, p90 0.21%, max 14.90% on K4_90_belastet's right condyle), and more than `MAX_WRAP_FRACTION` (25%) logs a WARNING. **Extension, not in the paper**: the trochlea (`alf`/`arf`, anterior of the notch plane) and the posterior condyle (`plf`/`prf`, behind the 60% plane), each split into the two sides by the same plane that separates the condyles (through the fitted line of intercondylar-fossa centres, `ml = slope*ap + intercept`, MAD-filtered, |slope| clamped to 0.5 with a WARNING). Cartilage voxels take the region of the nearest tAB triangle centroid (`FemurSubdivision.region_codes_at`), stored in `Femur.point_labels`; QC exactly as for the tibia (`Femur.transfer_qc`, WARNING over 1% beyond 6 mm, fed into `scan_qc_flags` as `femur_transfer_far:<fraction>`). `Femur.plot_regions()` draws the labelled tAB with the frame, the notch plane and the two 60% planes (the paper's Fig. 6 view). **The femoral subregions no longer need a `Tibia`** — but the thickness *maps* do, for the shared in-plane frame: `Femur.calculate_thickness(tibia, ...)` / `calculate_femoral_cartilage_thickness(image, tibia, ...)` take it for that alone, and without one the maps are keyed in a femoral frame that `find_thinnest_area` refuses to overlap with tibial maps (see the thickness bullet). `plot_segments(tibia=None, ...)` still ignores it. - **Cartilage thickness follows Wirth & Eckstein 2008 section II-C** (`morphometry/cartilage/thickness.py`, plan step 4; replaced the voxel-column `mesh` / `knn` methods outright, no legacy switch). Per subregion it is the **area-weighted Euclidean distance between the two surfaces**, both ways: `cMe` = each cAB triangle's exact distance to the articular cartilage surface AC, `bMe` = each AC triangle's distance back to cAB, `aMe = (cMe + bMe) / 2` (the number to quote), every triangle weighted by its own area. `tab_*` are the same over the whole tAB with denuded triangles counted as 0.0 mm, so `tab_aMe = aMe * cAB/tAB` exactly. `aMax` / `aMav` (mean of the largest 1% of the area) / `aSD` (area-weighted population SD) / `aMin` / `aMiv` come from the two directions pooled into one sample in which each direction carries half the weight — so the pooled mean *is* `aMe`; `weighted_statistics` drops zero-weight entries, so the denuded placeholder cannot read a clean region's minimum as 0. **There are two families and they must not be mixed**: the bare names are ThC.**cAB** and the `tab_` ones ThC.**tAB** (the same with denuded bone at 0.0 mm), so `aMe ± aSD` is self-consistent, `tab_aMin` is exactly 0 for any region with any denuded bone while `aMin` is the thinnest cartilage actually measured, and `tab_aMax` / `tab_aMav` differ from their cAB twins only for an almost wholly denuded region. The CSV carries both families in separate blocks; the JSON `statistics` block carries all of them. **AC** is `surface.articular_surface_mesh`: the outer surface of the bone+cartilage **union** (so no bone-cartilage interface appears in it and a one-voxel-thick layer is still recognised), minus the cartilage rim and the smoothed foot of the rim — a triangle is kept only if its normal is within 60° of the bone normal beneath it *and* the voxel half a voxel *down the bone's normal* carries the cartilage label. Keeping the rim reads 1.63 mm on the flat 2 mm plate phantom and keeping only its foot 1.67, against a true 2.00 (now 1.95); the damage is proportional to a subregion's perimeter-to-area ratio, i.e. exactly what separates the peripheral subregions from the central one. `surface.surface_distances` is VTK's exact point-to-triangle distance, not nearest-centroid (which would be up to ~0.1 mm short on a 0.1 mm² triangle mesh). Only the **joint-facing sheet** enters the per-position maps (`_joint_facing_sheet`): projecting a curved surface onto the shared plane folds it onto itself — cells whose contributing femoral centroids span more than 5 mm are 10/7/13/22% of the femoral cells at 0/30/60/90° of flexion (26-47% of the tAB *area*) and 14/5/2/18% of the cells the thinnest-point search uses, with the largest spreads 30-60 mm — so without it a cell mixes the trochlea with the posterior condyle and its recorded articular position lands *inside the bone* between the two sheets, which is where the 3D marker and the femoral arc coordinate read it from. The regional statistics are per triangle and do not move. `measure_thickness` returns a `ThicknessMaps`, a `dict` subclass, so every existing consumer still sees `{subregion: {(u, v): mm}}`, with `.statistics`, `.frame`, `.positions` (the articular-surface point of each cell, for 3D markers) and `.triangle_thickness` (aligned with the subdivision mesh, for the heatmap) attached. `method=` is kept on every entry point but **rejects every value** with a message naming the replacement, so old call sites and `--method knn` command lines fail loudly.
- **One in-plane frame shared by both bones: the tibial plateau plane** (`thickness.KneeFrame`, `knee_frame_from_tibia`). The maps are keyed by the integer `grid_mm` (0.5) cell of each triangle centroid's projection into that plane, with `e1` patient-right (the line joining the two plates' centres of gravity S), `e3` the mean plate normal and `e2 = e3 x e1` anterior; the origin is the midpoint of the two S. The collapsed direction is the plate normal, which is the direction the tibiofemoral joint is compressed along at **every** flexion angle, so the femoral contact patch — distal condyle at full extension, posterior condyle at 90° — stays over the plateau and the two maps keep overlapping (pinned by a flexion phantom in `tests/unit/test_cartilage_thickness.py`: in the tibial frame the common footprint stays > 1500 mm² at 0/30/60/90°, in a co-rotating femoral frame it collapses below 300 mm² at 90°). A femur measured without a `Tibia` gets a frame from its own subdivision (`knee_frame_from_femur`, `source='femur'`), which is only the contact plane at full extension; such maps are valid on their own but `find_thinnest_area` refuses to overlap them with tibial ones. This replaced per-voxel-column keys that were array axes 0 and 1 whatever axis a subregion was measured along — the femoral posterior zones were keyed by `(x, depth)`, so their columns collided and their values were placed at the wrong in-plane position at 60-90° of flexion. `Femur.depth_axis` / `_depth_axis` / `_zone_surface_points` / `_thickness_surface` / `build_cartilage_meshes` / `get_superior_and_inferior_surface_points` and `Tibia.superior_surface` / `.inferior_surface` are gone with them.

- `morphometry/cartilage/surface.py` is the shared bone-surface geometry for the Wirth & Eckstein 2008 subregions (`docs/wirth_eckstein_2008_plan.md` step 1; used by `tibia_regions.py` and `femur_regions.py`, which also take their region-transfer QC — `transfer_qc`, `TRANSFER_FAR_MM`, `TRANSFER_MAX_FAR_FRACTION` — from here; `tibia_regions` re-exports them, as callers have always imported them from there). `bone_surface_mesh` = marching cubes on the (largest-component) bone label in index space, mapped to **world mm, RAS frame for both backends** through the full index-to-world matrix (`index_to_world_affine`; SimpleITK's LPS is converted, so anatomical directions in world coordinates do not depend on the loader; winding fixed for reflecting directions, outward normals), windowed-sinc smoothed (`smooth_taubin`, 20 it., pass band 0.1: sphere area within 1%, surface moved ~0.02 mm). Where the bone touches the array border (FOV cut through the shafts) the mask is extended by replicated slices and the smoothed surface is cut **exactly** at the outer voxel boundary, so the mesh is *open* there with no artificial cap. `cartilage_coverage` (cAB) = triangle centroid within `tolerance_mm` of a voxel centre of that bone's cartilage label (KD-tree, world mm); default `0.6 ×` voxel diagonal (0.52 mm on `dfg_knees`) = the half diagonal a face-adjacent cartilage voxel can be away plus 20%. For a mask occupying a fraction `f` of the z extent whose **non-empty** slice areas have coefficient of variation `CV` (write `c² = 1 + CV²`), a near-empty apex slice has `|z| = sqrt(f) / sqrt(c² - f)`, so it fires iff **`f > 0.8 · c²`**; at full occupancy that is simply `CV < 0.5`. That form is exact under its premise — validated to a max relative error of **4.4e-15** over 500 random area vectors with a genuinely empty apex, with `f > 0.8c²` equivalent to `|z| > 2` identically — so the caveat is about the premise, not the algebra: **use it on thin-sliced data and compute the statistic directly on thick-sliced data.** Against the true `np.abs(zscore(...))` — **in the z-trimmed frame, with the apex slice included in `c²`**, the only frame where the comparison discriminates — it is accurate on NaKo (+4.2% median error, fire/no-fire verdict correct on 112 of 120) and fails on Augsburg (+108% median, worst case +24000%, verdicts 78 of 100); in the as-given frame it gives +10.7% and +75.0% with the verdicts trivially right because nothing fires either way, and dropping the apex from `c²` moves Augsburg's verdict count to 66, because at 1 mm the apex slice is a thin cap at **4.1%** of the mean slice area while at 10 mm it already cuts **52%** and is nowhere near empty. - **The femoral-torsion method labelled "Lee" is Schock et al.'s, and its gap with Murphy is anatomy rather than error** (`femur.py::get_femoral_neck_center_lee`; task #2, closed 2026-11-04 as **premise refuted**, not fixed). What is implemented is the automatic method of **Schock et al., Sci Rep 11:23244 (2021)** — the paper this pipeline derives from — which its authors describe as *"closest to the method of Lee"* and not as Lee's method: they define the neck **axis** as the reference line where Lee et al. (Med Biol Eng Comput 44:895–906, 2006) define the neck **centre**. So the contour-fitted neck axis is the published design, not a misreading, and the label is a shorthand. **A proximal neck landmark reads systematically lower than a distal one**, because the distal femoral neck is more posterior — Schock et al.'s own radiologists measured **16.1° by Lee against 32.2° by Murphy** (their algorithm vs their Lee reader: p = 0.859, not significantly different), and Lee et al. give the law `θ = 25.3·(L/D) − 5.4` for `L/D` 0.1–0.6, `L` being the distal distance from the proximal-most neck confluence and `D` the head diameter (mean 42.8 mm). On the 50 Augsburg reader-study hips this method's slice sits a median **12.8 mm** below the head centre and Murphy's **44.9 mm** — a 32.1 mm separation, for which that law predicts **≈19°** against the **18.97°** measured (our Lee 11.59°, Murphy 30.55°; their Murphy 32.2°). - **The replacement, in three parts.** The angle is accumulated on **coordinates** (no raster), so it inherits the first pass's exact invariance; the notch raster is sampled **once** on a grid anchored at `rint(head centre)` with `map_coordinates(order=0, mode='grid-constant', cval=0)`; and because `a` is a **distance**, and distances survive rotation, it is computed in that frame directly — the head centre is the grid origin by construction, so there is **no map-back, no `rot_offset`, no `rot_center` and no `int()` truncation**. `mode='grid-constant'` is deliberate and not interchangeable with `'constant'`, which returns `cval` outside the *closed* `[0, n−1]` and so discards the outer half voxel of every axis — itself an array-end dependence, measured at 15° on a shallow-FOV case in the alpha-angle work. The invariance is argued, not merely measured: under a translation `t` the anchor and the mask points shift together, so the rotated coordinates are **bitwise** identical and the sampled coordinates shift by exactly `t`; and the 1-voxel window margin is *provably* sufficient, because a border cell is ≥ 1 from every rotated mask point while nearest-neighbour rounding reaches at most 0.707.

- Physical (mm) coordinates stay floats: `get_femoral_shaft_axis_ct` returns float endpoints in physical space (consumers: `calculate_ccd_ct`, `calculate_femoral_offset_projected(ct=True)`). Only *index* coordinates are rounded/cast, and only where an array is indexed. Casting mm coordinates to `int` truncates toward zero, which makes a measurement depend on the image's position in the scanner frame.
- Failures inside batch scripts and `compute_torsion.py` are caught per-measurement and written out as `np.nan` so a single bad patient does not abort a cohort run. Keep this behavior when extending those scripts. **The exact tuple differs per file, and the rest of this document simplifies it — corrected 2026-11-06 after being checked per file.** `morphometry/docker/compute_torsion.py` catches `(RuntimeError, AssertionError, ValueError)` (6 sites), and that is the tuple quoted elsewhere here. But `scripts/process_augsburg_{reader_study,large_dataset}.py` catch **`(ValueError, IndexError, RuntimeError)`** (16 sites each) — so on the Augsburg path an **`IndexError` is caught** and an **`AssertionError` aborts the run**, which is the *opposite* of what the simplified tuple implies in both directions. `scripts/process_nako{,_large}.py` are different again and the most forgiving: every measurement sits under a bare `except Exception` (10 and 14 sites), so nothing escapes there at all. `scripts/process_nmdid.py` wraps its QC in its own `try` and logs a warning. **Read the file before relying on a tuple**: the five earlier mentions in this document are written as "the batch scripts" and are accurate only for `compute_torsion.py`. The practical consequences are unchanged wherever a function raises `ValueError` (caught everywhere) — which is every guard this document discusses — so no decision recorded here is invalidated; what changes is the *reason* those guards are safe on the Augsburg path.
- **A QC gate should be shown non-mutating at RUNTIME, not only by diff — and that check is cheap (established 2026-11-06).** "Purely additive" is normally argued from `git diff`: no measurement module touched, no golden moved. That is necessary and not sufficient, because a gate re-resolves the same landmarks from the same arrays and could in principle perturb them. The strong form is to measure, call the gate, measure again, and compare bitwise. Done for the condylar gate on PA000001 (both halves, independently by the implementer's reviewer and by the lead): the array is byte-equal afterwards and `calculate_knee_rotation_angle` returns **bit-identical** values either side of the gate (2.4396980035280196 left, 6.104684876928884 right). It holds by construction — the gate's `np.where` copies and its `mask[::-1]` is a read-only view — but it is worth demonstrating rather than asserting. **The Murphy and Lee gates now have the same check, and all three are pinned as tests rather than run by hand (2026-11-09).** On PA000001's two halves both hip gates return `''`, the hip array is byte-equal afterwards, and the Lee torsion, the Murphy torsion and the anteversion are all **bit-identical** either side of the two gate calls (the Lee values being 6.025752 and 13.043961, i.e. exactly their goldens, which is a free cross-check that the probe measured the shipped path); the condylar gate likewise leaves the knee rotation angle bit-identical with both bones gated. `tests/characterization/test_qc_gates_non_mutating.py` pins all of it, so the property is enforced rather than remembered. **Its two assertions are independent, and that was mutation-tested rather than assumed**: a value-neutral single-voxel write into the mask a gate was handed is caught **only** by the byte-equality check (the measurement does not move at all — one interior hole is invisible to the angle), while a 1e-9-degree perturbation with the array untouched is caught **only** by the bitwise value check. That second case is the reason the comparison is `np.array_equal` and not `pytest.approx`: `approx` would pass it. Runtime cost for the same gate, since both precedents quote theirs: ~65 ms for the two QC calls of one image half, i.e. about 0.9x one `calculate_knee_rotation_angle` over both halves and roughly **90 s over the whole 954-case Augsburg cohort** single-process — two orders cheaper in relative terms than the Murphy/Lee QC's +11.4% per NaKo case, because it duplicates two section searches rather than a femoral-head fit. That is an argument *for* the resolve-it-twice design rather than a cost to apologise for.
- **The QC wrappers' never-raises contract has a live justification, now verified rather than assumed.** In both Augsburg scripts the `get_murphy_neck_qc` / `get_lee_neck_qc` calls sit **outside any `try`** — in the gap between the measurement try block above them and the plotting one below, with the only enclosing try being the loader's `FileNotFoundError`. So an exception escaping either wrapper propagates out of `process_patient` into `pool.map` and **aborts the whole cohort run**. That is why both wrappers catch `Exception` and report a failed landmark as a flag string instead of raising, and why that contract must not be narrowed. `scripts/process_nako_large.py`'s QC call is by contrast inside a bare `except Exception`, and `process_nmdid.py` wraps its own.
